# JSON 数值对象序列化反序列化能力扩充方案

> 日期：2026-08-09
> 范围：flora-root `com.flora.codec.json`（JsonParser / JsonBuilder / JsonUtil 门面）
> 目标：在不破坏现有 API 的前提下，为数值（Number）的序列化与反序列化扩充可配置能力

---

## 一、现状分析

### 1.1 反序列化（JsonParser.parseNumber，`JsonParser.java:200-219`）

```
数字文本 → 是否含 '.' 或 'e'/'E'
              ├─ 是 → BigDecimal（无论值是否等价整数）
              └─ 否 → Long.parseLong 成功 → Long
                        └─ 溢出 → BigInteger
```

- 整数：`Long`（溢出升为 `BigInteger`）
- 小数/指数：一律 `BigDecimal`，原始文本不保留（`1e5`、`1.00` 在解析后即丢失原貌）
- 无任何解析策略配置项

### 1.2 序列化（JsonBuilder.serializeNumber，`JsonBuilder.java:152-180`）

```
Double/Float → NaN/Infinity → 抛 IllegalArgumentException
             整数值且 long 范围内 → 输出 (long)d（如 1.0 → "1"）
             否则 → toString()
其他 Number（Integer/Long/BigInteger/BigDecimal/Short/Byte/Atomic*）→ toString()
```

- 无任何序列化格式配置项
- 注意 `module-info.java` 未导出 `com.flora.codec.json` 包（对外仅 `com.flora.codec.JsonUtil` 门面），新增类型如需对外暴露要在门面或 module 层补导出。

### 1.3 现有测试锁定的行为

- `JsonParserTest.parseNumbers`：`"{\"i\":42,...}"` → `Long`；`3.14`、`1e5` → `BigDecimal`
- `JsonBuilderTest.serializeDoubleArray`：`new double[]{1.0, 2.0}` → `"[1,2]"`（浮点整数值转整数形态）
- `JsonBuilderTest`：`Double.NaN` / `POSITIVE_INFINITY` 序列化抛异常

## 二、问题与需求清单

| # | 问题 | 场景 | 现状后果 |
|---|---|---|---|
| 1 | **浮点整数值语义丢失** | `1.0` 序列化为 `"1"`，再解析回 `Long` | 浮点↔整数的类型语义在 round-trip 中改变 |
| 2 | **long 超出 JS 安全整数** | `9007199254740993` 序列化为数字 | 浏览器/JS 端精度丢失（需 Long-as-String） |
| 3 | **BigDecimal 输出格式不可控** | `1E+10` 由 `toString()` 输出 | 与 `toPlainString()` 语义不同，部分消费者解析偏好各异 |
| 4 | **解析数值类型不可选** | 消费端期望 `Double`/`Float`/`Integer` | 一律 `Long`/`BigDecimal`，需调用方自行转换 |
| 5 | **非有限数无可配置输出** | `NaN`/`Infinity` | 直接抛异常；宽松模式（输出 `null` 或引号字符串）不可用 |
| 6 | **原始数字文本丢失** | `1.00`、`1e5`、`-0` | 无法无损 round-trip；调用方拿不到"原文是什么" |
| 7 | **混合数值类型使用不便** | Map 中 Long/BigInteger/BigDecimal 混杂 | 比较、转换需手写分支 |
| 8 | **无自定义数值编码 hook** | 特殊数值类型或格式需求 | 只能改源码，无法扩展 |

---

## 三、方案列举

### 方案 A：解析端数值策略（NumberParsingPolicy）

反序列化时通过选项控制"整数 / 小数解析成什么类型"。

- **配置项**：
  - 整数策略：`Integer` / `Long`（默认，现状）/ `BigInteger`
  - 小数策略：`BigDecimal`（默认，现状）/ `Double` / `Float`
  - 指数归一化：`1e5` 是否按整数处理（现状为 `BigDecimal`）
- **入口**：`JsonParser.parse(String, NumberParsingPolicy)` 重载；`JsonUtil` 增加带策略的重载；不传则走现状。
- **优点**：直接解决 #4；默认行为不变，完全向后兼容。
- **缺点**：策略项越多，测试面越大；仍不解决无损 round-trip（#6）。

### 方案 B：序列化端数值格式策略（NumberFormatPolicy / JsonBuilderOptions）

序列化时通过选项控制数值输出格式。

- **配置项**：
  - `longAsString`：`Long`/`BigInteger`/`long[]` 序列化为 JSON 字符串（解决 JS 精度，对应 #2）
  - `keepFloatingPoint`：`1.0` 输出 `"1.0"` 而非 `"1"`（解决 #1）
  - `bigDecimalMode`：`PLAIN`（`toPlainString()`，如 `0.0000001`）/ `TO_STRING`（现状）/ `FORCE_EXPONENT`
  - `nonFiniteMode`：`THROW`（现状）/ `NULL`（输出 `null`）/ `QUOTED`（输出 `"NaN"`）（解决 #5）
- **入口**：`JsonBuilder.toJsonString(Object, JsonBuilderOptions)` 重载；`JsonUtil` 同步。
- **优点**：直接解决 #1/#2/#3/#5；兼容现状。
- **缺点**：配置项多；`longAsString` 需要区分"值本身是否超出安全范围"还是"一律字符串"两种粒度。

### 方案 C：无损原始文本保留（RawJsonNumber / JsonNumber）

反序列化返回一个**持有原始数字文本**的 `Number` 子类，类型决策延迟到取值时。

- **核心类型**：`JsonNumber extends Number`，字段含 `rawText`（原始 token）+ 惰性解析缓存。
  - `numberValue()`：按需转 `Long`/`BigDecimal`/`Double`
  - `rawText()`：返回原文（如 `"1.00"`、`"1e5"`、`"-0"`）
  - `isIntegral()` / `isExponent()`：文本形态判断
- **入口**：`JsonParser.parseLossless(String)`（新方法，不碰 `parse()`）；`JsonUtil.parseLossless`。
- **优点**：**彻底解决 #6**（无损 round-trip）；类型延迟决策，一个结构满足所有消费形态；与方案 A 兼容（可在 JsonNumber 上叠加策略）。
- **缺点**：返回类型不再是纯 `Long`/`BigDecimal`，`Map<String,Object>` 的元素类型变化（调用方需配合转换工具，见方案 E）；API 面扩大。

### 方案 D：可插拔 NumberCodec SPI

为数值序列化/反序列化提供 SPI 扩展点，允许注册自定义编解码器。

- **核心接口**：
  ```
  interface JsonNumberCodec {
      Number parse(String raw);              // 原始数字文本 → Java 数值
      String serialize(Number value);        // Java 数值 → JSON 数字文本
      boolean supports(Object value);        // 类型/值判定
  }
  ```
- **入口**：`JsonParser`/`JsonBuilder` 增加 `withCodec(JsonNumberCodec)` 注册，未命中时回退默认策略。
- **优点**：最灵活，覆盖 #8（自定义数值类型、科学计数法约定、业务数值封装类）；方案 A/B 可视为内置的默认 codec 组合。
- **缺点**：SPI 复杂度最高；需要明确的优先级与回退规则，否则难以排查"为什么走的是默认路径"。

### 方案 E：数值归一化与转换工具（JsonNumbers）

独立工具类，帮助调用方处理解析结果中的混合数值类型。

- **能力**：
  - `coerce(Number, Class<T>)`：`Long`/`BigInteger`/`BigDecimal` → `int`/`long`/`double`/`float`/`BigInteger`/`BigDecimal`，含溢出检查与舍入策略
  - `isIntegral(Number)` / `hasFraction(Number)`：数值形态判断
  - `compare(Number, Number)`：跨类型安全比较（先统一到 `BigDecimal`）
  - `toStringLossless(Number)`：`BigDecimal.toPlainString` 无指数输出
- **入口**：`com.flora.codec.json`（或门面）新增静态工具类。
- **优点**：解决 #7，同时是方案 C 的配套（`JsonNumber` 的 `numberValue()` 内部即可复用 `coerce`）。
- **缺点**：属于"补丁"而非"结构"改进，单独使用不解决根本问题。

## 四、方案对比

| 维度 | A 解析策略 | B 序列化格式 | C 无损保留 | D NumberCodec SPI | E 转换工具 |
|---|---|---|---|---|---|
| 解决的问题 | #4 | #1/#2/#3/#5 | #6 | #8 | #7 |
| API 侵入性 | 低（新增重载） | 低（新增重载） | 中（新增类型） | 中高（新增 SPI） | 低（新增工具类） |
| 向后兼容 | ✅ 默认行为不变 | ✅ 默认行为不变 | ⚠️ 仅新方法 `parseLossless` | ✅ 默认回退 | ✅ 纯新增 |
| 实现成本 | 低 | 低~中 | 中 | 中~高 | 低 |
| 通用性 | 高（各库普遍支持） | 高 | 高（Jackson/Gson 均有 raw 形态） | 中 | 高 |
| 组合关系 | 与 B 正交 | 与 A 正交 | 依赖 E 配套 | 可收纳 A/B | 被 C 复用 |

## 五、推荐实施路径

**分三步走，逐步增强，全部保持默认行为不变（向后兼容）：**

1. **第一批（方案 A + B）：解析/序列化端策略化**
   先解决最痛点：#2（JS 精度）、#1（浮点语义）、#4（类型可选用）。新增 `NumberParsingPolicy` 与 `JsonBuilderOptions` 两个值对象 + `JsonParser.parse(src, policy)` / `JsonBuilder.toJsonString(obj, options)` 重载，`JsonUtil` 门面同步补重载。配套补 `module-info` 导出或收敛到门面。

2. **第二批（方案 C + E）：无损 round-trip + 转换工具**
   引入 `JsonNumber`（持有 rawText）+ `parseLossless`；同步提供 `JsonNumbers.coerce/compare` 等工具。`JsonNumber.numberValue()` 内部复用 `JsonNumbers.coerce`，保持一个实现。这是对"数值对象"支持最本质的一步——数值不再是"解析后的一个数"，而是"一段可往返的数字文本"。

3. **第三批（方案 D，可选）：NumberCodec SPI**
   当出现定制数值需求（业务数值类型、特殊格式约定）时再引入 SPI。A/B 的默认行为作为 SPI 的默认 codec，避免双轨。

> 各批之间互相正交：A/B 管"策略"，C/E 管"无损与转换"，D 管"扩展"。任何一批都可独立落地，不阻塞其他批。
