# Java 领域实现编译器 / 解释器的工具选型

日期：2026-08-12
状态：技术调研与选型笔记

## 1. 背景与场景定位

"在 Java 领域写一个编译器"需要先明确目标，因为 JVM 生态的工具链因**目标产物**不同而完全不同。先区分四类场景：

| 场景 | 目标 | 典型代表 |
|---|---|---|
| A. 解释器 / AST 求值 | 解析源码 → 语法树 → 直接求值（不产出代码） | 各类 DSL、脚本引擎、`ramet` 模板引擎 |
| B. 编译到 JVM 字节码 | 解析源码 → 生成 `.class`，跑在 JVM 上 | Kotlin、Groovy、Scala、Jython |
| C. 自托管 / 生成其它语言 | 解析源码 → 生成 C / JS / 自编译 | 教学编译器、转译器（transpiler） |
| D. Java 字节码分析 / 改写 | 读 `.class` → 分析或改写 → 重写 `.class` | ASM、Byte Buddy、`tangle`（混淆器） |

前端的**解析**工具（词法 + 语法）四类通用；后端的**生成**工具才分道扬镳。本文按"前端工具"与"后端工具"两条线组织，并单列"一体化框架"。

## 2. 前端（词法 + 语法分析）工具

### 2.1 ANTLR（推荐，主流首选）

- **类型**：ALL(*) / adaptive LL(*) 解析器生成器，LL 族。根据语法 `.g4` 生成词法器 + 递归下降解析器 + 监听器 / 访问器骨架（Java / C# / Python / JS / Go 等多目标）。
- **特点**：
  - 语法与代码分离：改文法重生成，解析逻辑不与手写解析代码纠缠；
  - 自带 `ParseTreeListener` / `ParseTreeVisitor` 两种树遍历模型，语义分析挂 visitor 即可；
  - 错误恢复机制成熟（默认与自定义），能容忍部分语法错误继续解析；
  - 生态最大：大量现成语法库（Java、C、Python、SQL…），IDE 插件、调试工具齐全；
  - 支持左递归的直接表达式（`expr : expr '*' expr | ...`），自然表达运算符优先级。
- **局限**：生成代码较大、解析速度不是最快；LL 对某些文法表达力弱（间接左递归、需要回溯的情形受限）；语义动作（`{}` 内嵌）与语法混写会污染可维护性，建议纯语法 + visitor 分离。
- **版本**：ANTLR 4 是当前稳定主流（4.13 附近），v3 已弃用。
- **适用**：新语言前端首选，尤其是语法会迭代、需要多目标输出的项目。

### 2.2 JavaCC（及其后继 JavaCC21 / javacc-maven-plugin）

- **类型**：LL(k) 解析器生成器，社区版名 `JavaCC`，商业/重构版 `JavaCC21`。
- **特点**：
  - 生成 Java 解析器（不支持多目标输出）；
  - 支持**语义动作**直接嵌入文法规则（`{}`），代码生成直白、运行快、无运行时依赖；
  - 有内建 `JJTree` 工具从文法自动构建 AST。
- **局限**：LL(k) 需要手算 lookahead，间接左递归支持弱；语义动作与语法混写使文法难读难维护；生态与文档明显弱于 ANTLR；社区演进曾停滞，JavaCC21 是主要活跃分支。
- **适用**：需要极轻量、无运行时依赖、代码直白的项目，或从旧项目迁移的存量代码。

### 2.3 手写递归下降解析器（无工具）

- **类型**：手写词法器 + 递归下降语法器。
- **特点**：零依赖、完全可控、错误信息最友好、编译期与运行时开销最小。
- **局限**：开发量大、易错；文法改动要同步改代码；需要自己处理优先级、回溯。
- **适用**：语法小而稳定、对依赖极度敏感的项目。本项目已有自研 `com.flora.root.syntax.peg`（PEG 文法 → 运行时解析，见 §2.5），即此类路线的一种系统化形态。

### 2.4 PEG 解析器（Parsing Expression Grammar）

PEG 用**有序选择 + 贪婪匹配 + 回溯**替代上下文无关文法的二义性处理，一次解析、文法即规约，天然无左递归（需显式改写）。

- **代表**：`parboiled`（Java，流式定义文法，运行时解析，无代码生成）、`PEG.js`（JS）、`PyParsing`（Python）。
- **特点**：文法即代码（parboiled 用 Java 方法链定义规则），调试友好；回溯模型使错误定位和消歧更简单；无需生成步骤。
- **局限**：解析性能受回溯影响；PEG 回溯语义与典型"最长匹配词法"不同，需自行处理词法/语法分层；无左递归的隐式支持（要手动转换为迭代形式）。
- **适用**：语法规模中等的 DSL、语言原型、需要快速迭代的项目。

### 2.5 本项目自研 `com.flora.root.syntax.peg`（现状评估）

flora-root 已内置一套 PEG 解析框架（`Grammar.compile(def, options)` → `Recognizer` → `ParseTree`），支持 lexer/parser 双层、autoSkip、lookbehind、mode 切换、循环/左递归校验。

- **定位**：属于"手写 PEG 引擎"路线，是自研解析基础设施。
- **已解决**：词法/语法分层、空白跳过、错误行列报告、文法校验（可空性、环、左递归）。
- **待评估**：与 ANTLR 相比缺——语义动作框架（visitor 需自建）、表达式左递归的自动处理（PEG 需手写循环）、大规模语法的 IDE/调试工具。若用它做编译器前端，语义分析层（符号表、类型检查）与代码生成层都要自建。
- **结论**：作为通用解析引擎继续完善有价值；但若目标是从零实现一个正经语言的编译器，解析只是最小一环，语义与生成才是大头，是否用自研 PEG 取决于对"自研程度"的取舍。

## 3. 后端：生成 JVM 字节码（场景 B）

目标是产出 `.class`。三档粒度可选。

### 3.1 手写字节码 / 汇编

- 用字节码工具直接 emit 指令序列（见 §3.2），或手写 `.class` 结构。
- 灵活但成本极高，几乎无人从零做，通常以 ASM 等为底层。

### 3.2 ASM（字节码级，最底层、最常用）

- **类型**：字节码**生成与改写**库，操作 JVM 指令级（`Opcodes`），提供 visitor API（`ClassWriter` / `MethodVisitor`）与 tree API（`ClassNode` / `MethodNode`）。
- **特点**：
  - 最底层、性能最好、最灵活：可生成任意合法字节码，也可读入 `.class` 改写；
  - 几乎所有字节码工具（Byte Buddy、CGLIB、Groovy、Kotlin 编译器）都以它为基础；
  - 需要理解 JVM 指令集、栈帧、常量池、泛型签名等细节，门槛高；
  - 当前版本 9.x（支持 Java 21+ classfile 版本）。
- **适用**：需要**完全控制**字节码（生成器后端、混淆器、静态分析器、AOP 织入）。本项目 `flora-tangle`（字节码混淆器）即此类。

### 3.3 Byte Buddy（字节码级的高层封装）

- **类型**：建立在 ASM 之上的高层字节码生成库。
- **特点**：用类型安全的 Java API 描述"生成一个类 / 增强一个方法"（方法拦截、动态代理、超类生成、注解处理），`MethodDelegation`、`Advice` 等抽象大幅降低手写指令的工作量；也支持解析已有类改写。
- **局限**：仍面向"增强既有 Java 类"与"生成新类"，对"从 AST 发射任意方法体"的编译器场景，控制力仍不如直接 ASM，且抽象层有时是束缚。
- **适用**：面向切面、代理、运行时类生成的编译器辅助；语法树 → 方法的映射更接近手工 AST 遍历 + ASM 的场景。

### 3.4 从源到字节码的"编译器工具链"（不做字节码细节，仍生成 .class）

- **Janino**：把 Java 源码子集直接**编译成字节码**，轻量（一个库，无外部依赖），内嵌 Java 表达式 / 脚本求值（JSR-223），支持源码内存中编译。适合 DSL 或脚本热加载，不生成独立 `.class` 文件亦可。
- **GraalVM `compiler`（Graal）**：JVMCI 前端，把字节码（或经 Truffle）编译成机器码，主要用于 JIT / AOT 与 Truffle 语言运行时，是"把语言运行时跑到高性能"的路线，而非从源码生成 `.class`。
- **区别提醒**：把源码变成 `.class` 的"编译器"，与把 `.class` 变成机器码的"JIT 编译器"是两个概念——前者用 ASM/Byte Buddy/Janino，后者用 Graal/JIT。

## 4. 后端：生成其它语言（场景 C，转译器）

| 工具 | 目标 | 特点 |
|---|---|---|
| 手写转译 | 任意目标语言 | 模板拼接、可控；无工具支持 |
| StringTemplate / 模板引擎 | 生成源码 | 模板生成代码，适合代码生成器（本项目 `flora-ramet` 即模板生成引擎路线） |

转译器通常自己遍历 AST（visitor）按目标语言输出文本，工具只负责前端（§2）与字符串生成，无专门"转译器生成器"。

## 5. 一体化框架：把语言跑在 JVM 上（高层运行时路线）

| 框架 | 语言实现方式 | 特点 | 适用 |
|---|---|---|---|
| **ANTLR + visitor** | 前端解析 → 自建求值/生成 | 灵活，前后端皆可控 | 新语言、DSL、教学 |
| **Truffle（GraalVM）** | 用 AST 节点实现语言语义，交由 Graal 自优化 | 高性能（可达近原生）、语言互操作（Polyglot）、`gu` 工具支持；需按 Truffle DSL 编写节点，学习曲线陡 | 想让新语言在 JVM 上高性能运行（如 Golo、SimpleLanguage 教学实现） |
| **Janino** | 源码子集直接编译 | 轻量嵌入 | Java 表达式/脚本 |
| **（参照）Groovy/Kotlin** | 完整语言 + 编译器 + 运行时 | 成熟实现可作架构参照 | 不想从零造轮子时直接采用 |

Truffle 是"语言运行时"路线：你不写字节码，而是写 `RootNode` 语义，GraalVM 负责把语言优化到原生性能，并天然获得与其他语言的互操作。代价是强绑定 GraalVM 生态、节点编写范式约束、调试/工具链与 GraalVM 绑定。

## 6. Java 字节码分析与改写（场景 D）

| 库 | 特点 | 适用 |
|---|---|---|
| **ASM** | 最底层，读改写 + 生成，性能最好 | 混淆器、静态分析、插桩（`tangle` 路线） |
| **Byte Buddy** | ASM 上层，类型安全 API | 代理、AOP、运行时增强 |
| **BCEL**（Apache Commons BCEL） | 更老的字节码库，树模型，抽象层次高、性能一般 | 简单改写、教学 |
| **CFR / Fernflower** | 字节码 → Java 源码（反编译） | 逆向、学习字节码 |

## 7. 关键抉择矩阵

| 你的问题 | 推荐 |
|---|---|
| 想要语法迭代快、生态好、多目标输出 | **ANTLR 4** |
| 想要零依赖、轻量、代码直白 | **手写递归下降 / 自研 PEG（flora-root）** 或 JavaCC |
| 想从 AST 直接生成 `.class` 且要完全控制 | **AST visitor + ASM** |
| 想生成 `.class` 但不碰指令细节、轻量 | **Janino** |
| 想语言在 JVM 上高性能 + 互操作 | **Truffle（GraalVM）** |
| 只想解析求值（DSL / 模板） | **手写 / PEG / parboiled**，不必上 ANTLR |
| 要改写既有字节码（混淆、分析、AOP） | **ASM / Byte Buddy** |
| 参照成熟编译器架构 | Groovy（动态）、Kotlin（静态）源码 |

## 8. 对本项目的建议

- **解析前端**：flora-root 的 PEG 框架已能覆盖本项目 DSL / 模板场景，无需引入 ANTLR；若未来要实现一个完整语言编译器，再评估 ANTLR（尤其需要强语义动作与大规模文法时）。
- **字节码后端**：`flora-tangle`（混淆）走 ASM 是正确路线；若未来做"源码 → JVM 字节码"的编译器，AST visitor + ASM 是推荐形态；需要快速嵌入 Java 表达式求值可引入 Janino。
- **不做选择**：除非明确需要 GraalVM 高性能语言运行时或跨语言互操作，否则不引入 Truffle——其学习成本与生态绑定在当前项目阶段不划算。
