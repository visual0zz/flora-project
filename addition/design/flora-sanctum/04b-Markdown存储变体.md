# 04b Markdown 存储变体

> 本文是 04 存储设计 与 05 密码库适配器 的一个变体：把"底层对象库"具体化为"文件夹里的 markdown 文档集合"。
> 核心性质不变（明文局部修改 → 密文局部修改、局部提交、可合并并发、远端即备份），
> 差别在于**文件形态**：仓库就是一文件夹 markdown，管理器把它们当作 **base58 块的集合**来读写。
>
> **硬性外观约束**：三个顶层组（各含 root DEK）、组、口令条目、自定义字段、SSH 密钥、图标——所有 markdown 文件在文件系统层面必须**看起来没有任何区别**。

## 为什么用 markdown

不是伪装。目标是让仓库**同时**是：

- 一个可被管理器正常读写、局部增量提交的密码库；
- 一堆用户可自行打开、阅读、甚至改写的普通 markdown 文档。

用户能看到的正文（说明、备注、组织笔记）是明文、可自由编辑；管理器只读写自己约定的 base58 块，其余一律忽略。这样"写文档"和"记密码"共存于同一套文件里，用户不必在两种形态间搬运。

## 存储层语义：base58 块的集合

存储层**不感知文件的功能、也不感知文件内的分块语义**。它的世界只有两样东西：

- 一个 markdown 文件；
- 文件里散布的若干 **base58 块**。

管理器把仓库看成一张 **base58 块集合**，块是读写的最小单元。上层的所有处理（哪些是明文/密文/文件夹/条目/自定义字段）都针对**块**进行，与"块存在哪个文件、文件里还有没有别的内容"无关。

**块没有固定边界标记**。管理器对仓库里**任意一段看起来像 base58 的字符串**都尝试 base58 解码，解码后看前几个字节是不是本应用的 **magic number**——是则确认为一个数据块，否则当作普通文本忽略。

```
一个 markdown 文件里，任何位置都可能埋着数据块（无显式标记）：

# 我的服务器笔记

正文随意，一个长串可能就是一块：8f3TQxD2nX4YzRq9pW7cBvKmJh5LgEwUaFdGsN1t...

中间再放一点，两段之间不需要任何特殊标签。
```

- **块候选 = 连续的一串 base58 字符**（base58 字母表 `123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz`，不含易混淆的 0/O/l/I）。管理器用扫描器把文本切成候选串，逐个尝试。
  - **最小长度阈值**：候选串长度 ≥ 12 个字符才尝试解码（短串几乎不可能是含 magic 的数据块，避免对普通正文里零散 base58 字符的无效尝试）。
  - **大小写敏感**：base58 字母表区分大小写，扫描不规范化、按原样匹配。
  - **边界切分**：候选串遇到非 base58 字符即终止；换行、空格、markdown 标点（`**`、`[]()`、`` ` `` 等）都会切分候选串。故块必须写成连续无空白/标点的单串。
  - **独立文件整读**：独立文件（整文件只含一个块）读取时**先剥离首尾空白字符与换行符号**，剩余整段即为该块（见"新建"）；共享文件按候选串规则切分。
  - **长度对齐**：base58 非严格字节对齐，解码要求串合法（每字节序列对应合法编码），非法即跳过。
- **识别靠 magic，不靠标签**：候选串 base58 解码后，头部校验 magic（固定字节序列）匹配才认定为数据块。用户正文里的任意长串、甚至误写的类 base58 串，magic 不匹配即被忽略，不可能被误读。
- **一个文件可有零个或多个块**；块可以相邻、可以相隔任意 markdown，没有定位标签。
- 管理器**不关心**块所在文件的功能、也不做"哪个块该在哪个文件"的编排；上层只消费"块列表"。块的文件/行位置仅作写回时的定位记录（见"读写管线"）。

## 块自描述

每个 base58 块解码后是**自描述**的字节序列，**块本身就是单一的信封**（没有"外层块 + 内层信封"两层）。信封结构（见 02）：

```
magic(4B) + version(1B) + flags(1B) + uuid(16B) + keyId(4B) + nonce(12B) + ciphertext + tag(16B)
```

- **magic（4B）= `0x87 0xC2 0x55 0xAD`**：固定魔数，判明这是不是本应用的数据块（避免把用户乱写的 base58 当数据）。
- **随机字节异或混淆（不显式存 xorByte）**：整个信封字节序列与每块随机 xorByte 逐字节异或后落盘；xorByte 不落盘，读取时从落盘首字节反推（`xorByte = bytes[0] ⊕ magic[0]`）解异或、校验 magic（见 02）。每块落盘字节随机化，外部看不到固定 magic/内容模式。
- **flags 位标记**：`0x01`=密文 / `0x02`=明文。明文块负载为明文字节（无 keyId/nonce/tag），密文块负载为加密后的密文（见下）。
- **uuid（16B）**：本数据对象自己的 UUID（见"上层：对象与互相指向"）。**AAD = 整个信封头（magic/version/flags/uuid/keyId/nonce）**，tag 覆盖信封全部信息 + 密文，防密文被搬运到别的对象、防算法版本降级、防头部字段被篡改。
- **keyId（4B，仅密文）** = `byte1(1B) ‖ SHA256(DEK‖byte1)[0:3]`，byte1 逐块随机；解锁后用增量 keyId 索引定位候选 DEK，靠 GCM-SIV tag 试解确证（见 02）。
- **负载**：明文负载或密文。

明文块示例：`magic + version + flags(0x02) + uuid + plaintext`；密文块：`magic + version + flags(0x01) + uuid + keyId + nonce + ciphertext + tag`。两者由 flags 区分，无需明文标注。

存储层**不解构负载语义**：不做"是密文/明文、是条目/字段"这类判读（由上层完成）；只做读写所需的**信封级操作**——识别块边界、读出原始字节、读取头部 `uuid` 与 `keyId`（用于写回定位与路由）、把新字节写回同一位置。

## 读写管线

**读**：遍历全部 markdown 文件 → 扫描每处"像 base58 的连续串" → 逐个 base58 解码 → **反推 xorByte（`bytes[0]⊕magic[0]`）解异或** → 校验 magic → 得一批数据块（可能含明文、密文、或用户误写的无效串）。上层拿到块列表后各自解析：
- magic 不匹配 → 视为用户正文干扰，跳过；
- 是密文 → 用信封内 keyId 查增量索引得候选 DEK、tag 试解；
- 是明文 → 直接读负载。

**写（原位替换）**：要更新某块时，**写前重新定位一次**，再原位替换：
- 内存维护一张表：记录每个块是从哪个文件的**哪一行**读到的（读取时填充）。
- 写回时，**从记录的那一行出发，向两侧重新定位**当前该块的位置（优先找离记录行最近的有效块；按 uuid 确认是本对象）。
- 在找到的位置用新 base58 串替换旧串；若找不到或出现歧义（该位置已无有效块、或同 uuid 多处）则**中止并提示**，绝不盲目写入。
- 其余文件、其余块、用户正文一律不动 → 局部修改只引起局部密文/明文变化。

**为什么不做临时文件/快照替换**：写回本身只改一个串，不重写整个文件；写前重定位即可确认落点。无 temp + rename、无"先比对快照再写"的整文件流程——减少文件系统操作，也避免竞态下整文件互相覆盖。

**重定位失效的情形**（用户改了正文导致记录行不再有效）：记录行上下已无匹配的 uuid 块、或被拆行/改动 → 中止写入并提示，不猜测落点。块的识别与写回全程以 uuid 为准，不依赖"原串仍在原处"。

**写回失败后的处理**：中止后该次写操作整体失败，UI 提示"对象已被外部修改/删除"，不产生部分写入；用户可选择：重扫仓库后重试、将对象作为新副本重建（用 search 定位或新建）、或放弃。绝不在模糊落点处盲目替换。多块 ChangeSet 中任一块写回失败即整体回滚（不提交、不留下半更新），git 历史兜底。

**新建**：默认新建**独立文件**——整文件只承载一个块，无其它内容：

```markdown
<base58 块串>
```

- 文件里**只有块串**（不含标题/正文/说明）。
- **默认文件名 = 对象 UUID**：`<uuid>.md`（文件命名空间 = 对象 UUID，与"文件名不承载语义、以块内 UUID 为准"一致）。用户起名是**可选例外**，会暴露条目名，见"文件名策略"与"隐私边界"。
- **识别**：扫描器取文件内容后先**剥离首尾空白字符与换行符号**，剩余即为一段连续 base58 串 → 该块。文件里只有这一块。
- 判定独立文件 = 剥离空白后恰好一段合法 base58 串（1 个块）；文件含 ≥2 个块、或有块之外的用户正文 → 共享文件。
- 独立文件便于删改（可整文件物理删、无需软删除）。

**去重**：同一数据若在多个位置存在副本（用户手抄、多块），只需修改其中一处——上层以 UUID 为准，块间彼此独立，改哪个都是有效的新版本（见"一致性"）。

**删除**：删除某对象 = 移除其块的 base58 串。删除前先判断该块所在文件：
- **独立文件**（整文件只含这一个块）：可直接物理删除该文件（或其 base58 串）。
- **共享文件**（文件里还嵌着其它块 / 用户正文）：**不能整文件删**，需**软删除**该块（见下），保留文件其余内容与正文。
- 删除也可交由 gc 处理（标记为孤立后确认清除）。`delete` 同样需重定位，失败则中止提示（见"写回失败"）。

**软删除标记**：在目标 base58 串的**第一个字符之后插入一个专用非 base58 标记符 `!`**（base58 字母表不含 `!`）。效果：
- 插入后整串变为 `<首字符>!<其余部分>`——`!` 在中间，把原本连续的 base58 串**从中间断开**，不再是单一合法候选串，扫描器不会解码/magic 识别 → 该块从正常读取中失效。
- `!` 位置可辨认（串首后一位）：管理器据此识别"这是被软删除的块"，从而**跳过、不再读取**。
- **首字符保留**：原串首字符信息不丢失，便于核对/恢复判断。
- 文件其余块、用户正文完全不动。
- **物理清理交给人**：软删除只做"标记失效、不再读取"；该串的物理清除（从文件移除/重写）由**用户人工处理**，管理器不自动删除。

## 孤立块：搜索与 GC

数据结构的完整性由**更上层**保证（见"一致性"）；底层不维护任何连通性。因此仓库中可能存在**无法连接到整个引用网络的孤立块**（条目删了但字段块还在、用户残留的副本、半写入的中间态）。底层为此提供两个能力：

- **search(块)**：按 UUID / 内容特征在所有块中查找——定位某个对象当前的所有副本（去重、恢复、核查）。
- **gc()**：扫描全部块，解析引用关系，把不连入任何对象的孤立块列入清单，由上层确认后**软删除**（独立文件可物理删，共享文件加软删除标记）。gc **只做标记与忽略，不物理清理**——被软删除的块从读取/目录中排除，其文件残留由**用户人工处理**；管理器不自动重写文件去掉软删除串。

**可达树（reachability）算法**——从根出发沿引用遍历，能到达的块保留，不能到达的 = 孤立块：

- **根集合**（遍历起点，parent 为根概念 tag 或明文块）：
  - manifest 明文块（parent=manifest）；
  - **parent 为根概念 tag 的块**：三个顶层 group（`data`/`icon`/`sshKey`，KEK 能解开，各持独立 KEK 包裹的 DEK）与用户顶层文件夹/条目（parent=`data`）、remote 字段（parent=`remote`）——作为对象树与密钥树入口。
- **归属边（parent，层级，自下往上，决定树结构与加密归属）**：
  - group → `parent`（父组；顶层为根概念 tag `data`/`icon`/`sshKey`）；
  - entry → `parent`（所属组；顶层为 `data`）；
  - field → `parent`（所属条目/组，`fieldName` 为字段名；remote 字段为 `remote`）；
  - icon → `parent`（icon root group）；
  - sshKey → `parent`（sshKey root group）。
- **引用边（非归属，仅可达性，与层级彻底分离）**：
  - group/entry → `icon`（引用 icon 对象）；
  - remote（field kind）→ `keyRef`（引用 sshKey 对象或系统 key 名）。
- **遍历**：队列从根出发，沿归属边与引用边可达的块标记为保留；`可达 = 根 ∪ 沿边能到达的全部块`；`孤立 = 全部块 − 可达`。GC 从根概念出发，按归属边聚合树结构，引用边保证被引用对象（icon/sshKey）可达。
- **顶层组与 DEK**：三个顶层 group 是根，恒保留（各携 root DEK）；各文件夹 group 的 DEK 随 group 对象保留。上层的"显式删除某密钥"另行操作。
- 上层逐项确认后才实际删除；删除只影响该块自身，不触碰引用图其它节点。

孤立块**无害**（git 历史兜底），gc 是显式、可审查的操作，不做自动清理。

## 上层：对象与互相指向

在块集合之上，上层把每个块分配给一个"数据对象"语义，所有对象互相**通过 UUID 指向**：

- 文件夹（组，含各自绑定的文件夹 DEK）、口令条目、条目内部的自定义字段（含 `kind:"externalKey"`/`kind:"remote"` 外部密钥/远端配置）、SSH 密钥、图标——都是对象，各占一个（或几个）块。
- **每个数据对象在块内自述自己的 UUID**；引用他人时写入对方 UUID（如条目记录里字段名 → 字段对象 UUID 的映射，见 05）。
- 对象语义（type、归属、字段映射）在**解密负载**里（全 JSON，见 05），不在 markdown 明文；字段名/条目名/归属从不进入明文。
- **解密路由**：每个密文块用头部 keyId 决定用哪个 DEK 解密；DEK 来自**所属 root 的 DEK 树**（普通对象 root 链 / icon root / sshKey root，三个顶层 group 随机 uuid、KEK 试解识别，见 02/05），一对一或一对多由 keyId 指向决定，普通块负载不新增 keyRef 字段。
- 目录 = 解锁时扫描全部块、按解密负载的 type 分类、在内存构建引用图；锁定即丢弃，无持久索引。

## 文件夹 DEK（密钥树）

与 02 一致，落盘的是**用父密钥包裹的 DEK**，**不是主密码本身**。三个顶层 root 的 DEK 存于各自顶层 group（普通对象/icon/sshKey，随机 uuid、KEK 试解识别，用 KEK 包裹）；普通对象树子文件夹 DEK 存于各 group（用父 DEK 包裹），见 05。换主密码只重写三个顶层 group 的 DEK（新 KEK 重新包裹）+ 更新 manifest 的 MAC，普通对象树子文件夹 DEK 链与普通对象块不动。

## manifest 块（明文块，外观与其余对象统一）

仓库必须有一条**明文**信息（KDF 参数 + salt + 算法版本）才能先生效 KEK 再去解锁——它不能放进密文块（解不开就死锁）。这条信息同样做成一个 base58 **块**，且是**明文块**（`flags(0x02)`），与其余对象同构、外观统一，**没有独立特殊文件**：

```markdown
# 一个普通 markdown（看起来与其它对象无差别）

正文随意。中间埋着 manifest 的 base58 块，看起来和其它任何块一样：

<base58：明文块，负载 = JSON>
```

manifest 的明文 JSON 负载：

```json
{
  "version": 1,
  "type": "manifest",
  "cryptoVersion": "gcm-siv-1",
  "kdf": "argon2id",
  "salt": "<base64>",
  "params": { "m": 262144, "i": 3, "p": 4 },
  "warehouseTime": 1,
  "updateTimestamp": 1,
  "mac": "<base64>"
}
```

- 负载统一为 JSON（含 `version`/`type`，与其余对象同构）。
- `cryptoVersion`：算法套件版本，见 02 版本化适配。
- `kdf`/`salt`/`params`：解锁前必须的 KDF 参数（派生 KEK）。
- `mac`：KEK 派生验证密钥算的 MAC，防篡改/降级。
- **如何识别它**：manifest 是**明文块**（`flags(0x02)`），解锁前即可 base58 解码直接读负载 JSON，看 `type == "manifest"` 判定——**不依赖固定 UUID、不依赖文件名**。扫描全部块，找到唯一的明文块且 type 为 manifest 者即取作 manifest。
- 明文 + MAC（同 02）：解锁后先验 MAC，篡改/降级则拒绝打开。
- 它仍是**明文**，故外部可见其存在（这是必要的引导数据）；但它也是一个普通块，不需要特殊文件、不特殊命名。

## 文件与目录布局

```
vault/                          -- 库根（普通文件夹 / git 仓库根）
└── <uuid>.md                    -- 全部块平铺在库根，外观统一（含 manifest 明文块、顶层 group 与普通对象）
```

- 文件名**不承载语义**：管理器以块内自述的 UUID 为准，不依赖文件名。**默认文件名 = 对象 UUID（`<uuid>.md`）**；用户起名是可选例外，会暴露条目名（见"隐私边界"）。
- **无 `data/` 层**：所有对象 markdown 直接平铺在库根；存储层不依赖任何子目录结构，扫描库根所有 markdown 即可。

## 库形态与 Git 关系

**库不强绑定 git**：库就是一个普通文件夹，管理器随时可读写。git 是可选的外层，取决于该文件夹的实际处境：

- **独立文件夹（不在 git 仓库内）**：管理器直接读写，无需 git。
- **文件夹在 git 仓库内，且仓库基本只有 markdown**（判定为"本应用的库"）：提供同步功能——用 JGit 自动 init 若缺、commit / pull --rebase / push 与远端同步（见 06）。
- **文件夹在 git 仓库内，但仓库含复杂文件夹结构或其他文件**（判定为"某个更大项目的一部分"）：**不主动管理 git、不做同步**，只把自己的存储读写做在选定的子目录内；git 提交/同步由该外层项目自身或用户处理，管理器不碰。

**判断方法**（打开库时检测）：库目录及其向上若干层是否存在 `.git`；若存在，检查库根是否**全部是 markdown 文件**（可含无块/纯用户正文文件，但无其它扩展名/复杂子目录）。**只要库根全是 markdown 即视为"完全托管仓库"**，提供同步按钮、整仓库纳入 git 提交与同步（见 06）；否则只读写，不操作 git。

- **完全托管**：库根所有 markdown（含无块的、用户改动的）都纳入 commit/push/pull；管理器只读写自己的块，同步时把所有文件一起提交。
- 同步与否不影响**存储语义**：无论是否在 git 里，块识别、读写、写回原位完全一致。
- 远端配置/密钥对象照常存为块（见 06），仅当启用同步时被读取用于 JGit。

## 局部性与提交

- 改一个块 = 只替换那一处 base58 串，git 只见对应文件的一个局部 diff；一次 ChangeSet 一个 commit（仅当启用 git 时）。
- 用户手改某文档正文 → 仅该文件在 git diff 中变化；只要不改块本身，管理器下次读取不受影响。
- 不启用 git 时，改动直接落盘，无 commit 概念。

## 一致性

- **底层不保证连通性**：块集合可能含孤立块、重复块，这是可接受状态。
- **完整性由上层维护**：上层以块内 UUID 构建引用图，损坏/缺失只影响该对象，目录可随时重建（见 05）。
- **重复块**：上层以 UUID 识别"同一对象"，任意一个副本被更新都视为新版本；gc 可收敛冗余。

## 限制与恢复

- **manifest 块丢失/损坏**：manifest 是明文引导块（负载 type=manifest）。若其所在文件被删或块被拆坏，仓库失去 KDF 参数 + salt，**无法解锁**。恢复路径：用 git 历史（启用同步时）还原该块所在文件；未启用 git 时需用户从备份恢复。不提供"从密码重建 manifest"（无法逆向参数），故强烈建议启用 git 或定期备份。
- **顶层 root group（DEK）丢失**：仓库无法解锁（对应 root DEK 遗失）。同理靠 git 历史/备份恢复；换主密码仅重写三个顶层 group + manifest MAC，不涉及其余块。
- **单块大小上限**：一块 = 单个 base58 串，建议 ≤ 64 KB 原始字节；超过用 `raw`/压缩或分块（见 05 读取模式扩展），避免超长串难以扫描与手写维护。
- **对象与块映射**：一个逻辑对象默认**一个块**；`icon`/大字段等大对象可分多块，分块规则由 05 读取模式扩展定义（当前不启用）。

## 隐私边界（相对二进制方案的取舍）

- **对象块不可区分**：三个顶层 group、组、条目、字段、SSH 密钥、图标外观统一；是否密文、所属密钥组、是顶层组还是条目均不在明文可见（判定信息在块内）。
- **仍泄露的对象级信息**：仓库里存在若干长 base58 串、文件数量与大小。若这些不可接受，应退回 02/04 纯二进制信封（连 markdown 明文结构都不存在）。
- **字段名/条目名/归属关系安全**：只在解密负载内，markdown 明文不含任何用户命名。
