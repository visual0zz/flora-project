# 02 加密设计

## 密钥层次

```
master password
   └─ Argon2id (Bouncy Castle Argon2BytesGenerator) ─> KEK (256 bit)
        ├─ 包裹 普通对象 root DEK（普通对象 root group）
        │    └─ 包裹 子文件夹 DEK（链式，普通对象树内，可任意深度）
        ├─ 包裹 icon root DEK（icon root group）
        └─ 包裹 sshKey root DEK（sshKey root group）
普通对象树内各文件夹 DEK → HKDF-SHA256 → encKey → AES-256-GCM-SIV 加密该文件夹内的条目/字段
icon → icon root DEK；sshKey → sshKey root DEK
```

- KEK：由主密码经 Argon2id 派生，不落盘。
- **三个顶层 group**：普通对象 root / icon root / sshKey root，都 `parent==null`，各持一个**独立随机（256 位）、用 KEK 包裹**的 DEK。
- **普通对象树（文件夹 DEK 链）**：普通对象 root DEK → 子文件夹 DEK 链式（父 DEK 包子 DEK，可任意深度）。每个文件夹内条目/字段用该文件夹的 DEK（经 HKDF 派生 encKey）加密，keyId 指向所属文件夹 DEK。
- **icon / sshKey**：各自用所属 root group 的 DEK（icon root DEK / sshKey root DEK），parent 指向对应 root。
- 各 DEK 只在解锁期间驻留内存；解锁时从 KEK 起递归解出三个根 DEK，并沿普通对象树解出子文件夹 DEK。
- **根 group 识别**：三个顶层 group 都用随机 uuid，不特殊命名；解锁时用 KEK 遍历试解各 group，找到"**能被 KEK 解开且 `parent == null`**"者（最多三个）即顶层 group（只有三个 root DEK 用 KEK 包裹，故 KEK 解开的顶层 group 即这三者；`parent==null` 作双重确认）。顶层 group 的**加密 `role` 字段**（`objects`/`icon`/`sshKey`，见 05）用于区分三者用途，用于新对象定位所属 root。
- **换主密码 = 只重写三个顶层 group**：用新 KEK 重新包裹三个根 DEK；普通对象树子文件夹 DEK 链**不动**。+ 更新 manifest 的 MAC（KEK 派生验证密钥随主密码变化）。salt 终身不变。
- 子密钥：encKey 由 HKDF-SHA256 从各 DEK 派生。

## 算法接口策略

- **标准算法走 JDK JCA 接口**（`javax.crypto`）：HMAC-SHA256、SHA-256、密钥生成、SecureRandom；代码只依赖标准接口，可移植、可换 provider。
- **AEAD 用 BC 原生接口**：AES-256-GCM-SIV（RFC 8452）不在 JDK provider，用 `org.bouncycastle.crypto` 轻量 API（抗 nonce 误用，允许结构化/随机 nonce 两可）。
- **JDK 没有的算法用 BC 原生接口**：Argon2id（`Argon2BytesGenerator`）JCA 无对应，必须 BC；HKDF 优先 BC（JDK 新版本 KDF API 可用则优先）。
- 结论：`bcprov` 依赖不可省；除 AEAD/Argon2/HKDF 外尽量面向 JCA 编写，降低对 provider 的耦合。

## 熵混合（抗供应链）

所有**安全随机**（nonce、keyId 的 byte1、DEK、salt、UUID 生成等）不以单一 `SecureRandom` 为唯一来源，采用**混合熵**，降低对单一伪随机数生成器/其 provider 被投毒或退化的供应链风险：

- **主源**：系统 CSPRNG（`SecureRandom` / `SecureRandom.getInstanceStrong()`）。
- **叠加源**：一个独立、自维护的熵累积器（基于进程内不可控抖动，如线程调度、GC 时机、`System.nanoTime` 低位的混合）持续积累熵。
- **混合**：用 **HKDF-SHA256**（提取-扩展）合并两路熵——
  - `PRK = HKDF-Extract(salt=叠加源, IKM=主源)`：提取，把两路熵摊匀成一条均匀伪随机密钥；
  - 输出 = `HKDF-Expand(PRK, info="sanctum-entropy-mix", L)`：扩展成所需长度。
  - 任一源退化时，HMAC 单向性 + 另一源仍保证输出不可预测。
- **约束**：混合**不得降低**主 CSPRNG 的安全强度；整体仍以 CSPRNG 为骨干，叠加源仅作"不透明化"与"冗余"，不替代系统安全随机。禁止退化为纯非密码学 `Random`。
- 通过一个统一的安全随机入口提供（crypto 层内部），存储/上层不感知混合细节。与 encKey / macKey 的派生复用同一 HKDF 机制，零新增依赖。

## 版本化算法适配层

- `manifest` 记录 `cryptoVersion` 与 KDF 参数；SECRET 对象头部已有逐对象 `version` 字节（见下）。
- 适配层 = CodecRegistry（version → Codec 工厂）：
  - `Codec forRead(int version)`：按对象头部版本分发到对应实现，**旧仓库照常读（向后兼容）**；
  - `Codec latest()`：写路径永远用最新版本。
- 打开旧仓库：读用 manifest 记录的版本；首次写入自动把 manifest 升级到最新，之后新对象用新格式。
- **惰性迁移**：旧对象保持旧格式直到被再次写入（符合"局部修改"哲学）；另提供显式迁移命令批量重写。
- 发布新算法版本 = registry 注册新实现 + bump 版本；旧实现保留供读，不删除。
- **防降级**：manifest 为明文，必须附带完整性校验——解锁后以 KEK 派生的验证密钥校验其 MAC（覆盖 KDF 参数等全部内容），篡改则拒绝打开。

## 编解码接口：Codec（内部，不对外暴露）

crypto 层提供 Codec 实现（CipherCodec），供存储引擎**每次读写注入**（见 04）；仅供进程内上层调用，不对外暴露：

```java
public final class CipherCodec implements Codec {
    CipherCodec(SecretKey encKey, byte[] dek);             // 解锁流程构造；dek 用于计算 keyId
    public byte[] encode(byte[] data);                     // 加密 + magic 头 + keyId
    public byte[] decode(byte[] data);                     // 嗅探 magic 判别并解密
}
```

- 密钥管理（DEK/KEK/派生/生命周期）全在 crypto 层：解锁 = 构造 CipherCodec；锁定 = 丢弃引用。
- **keyId 的 byte1 与 byte2 在 `encode()` 内部生成**：byte1 用混合熵随机源（见"熵混合"），`byte2 = SHA256(DEK‖byte1)[0:3]` 写入信封头——因此 CipherCodec 需持有 DEK（除 encKey 外）以计算 byte2；此处的 DEK 仅供内存计算，**明文 DEK 不落盘**（落盘的是 group 对象里被父密钥包裹的密文 DEK，见下）、不解出。存储引擎仍不感知密码学，不依赖 crypto（依赖反转，见 04）。

## 对象信封格式（完整性）

**验证码与内容同文件内联**：单文件原子写（temp + rename）保证内容与验证码不会撕裂；对象自包含、可自验，符合统一读写管线。分开存放无安全增益——验证码与内容同处一个存储域时，恶意储存方可一并改写；分开反而引入双文件一致性问题。

**当前仓库除 manifest 明文引导块外全密文**：所有对象（条目/组/字段/远端配置/图标）一律 SECRET（读取模式在引用处声明，见 04/05），故只需一种信封；`uuid` 为对象身份，`flags` 位标记（`0x01`=密文 / `0x02`=明文，见 04b）：

```
magic(4B) + version(1B) + flags(1B) + uuid(16B) + keyId(4B) + nonce(12B) + ciphertext + tag(16B)
```

- **magic（4B）= `0x87 0xC2 0x55 0xAD`**（`0x87C255AD`）：固定魔数，用于识别本应用数据块（见 04b），防止把用户乱写的 base58 当数据。随 cryptoVersion 演进时保持稳定。
- **随机字节异或混淆（不显式存 xorByte）**：整个信封字节序列（`magic…version…flags…uuid…keyId…nonce…ciphertext…tag`，含 magic 本身）在**落盘/读盘时**与一个**每块随机生成的 xorByte** 逐字节异或。xorByte **不落盘**，读取时从落盘第 1 字节反推：`xorByte = 落盘bytes[0] ⊕ 已知magic[0]`，再用它解异或全序列、校验完整 magic。这样每块落盘字节完全随机化——外部看不到固定 magic、看不到内容模式（防指纹/反聚类增强）。异或是**存储层编码**，不改变 GCM-SIV 加密逻辑（加密用真实值）。
- **uuid（16B）**：对象自身的 UUID，置于信封头——块自述身份，供上层引用/去重；作为 AEAD AAD 的一部分（见下），防密文被搬运到别的对象、防算法版本降级。
- **keyId（4B）= `byte1 ‖ byte2`**，其中 `byte1`（1B）为**每个块写入时随机生成**（混合熵源，见"熵混合"），`byte2`（3B）= `SHA256(DEK ‖ byte1)[0:3]`。用途与构造如下：
  - **反聚类**：因 byte1 逐块随机，keyId 与 DEK 无直接可比对关系，外部无法判断哪些块共享同一 DEK（看似每块独立随机标签）。
  - **可定位（增量索引）**：每获得一个候选 DEK（初始来自 KEK 解开的三个顶层 root DEK，后续随普通对象树文件夹 DEK 递归解出，见"解锁流程"），遍历 byte1 的全部 256 个值，各算一次 `byte2 = SHA256(DEK‖byte1)[0:3]`，得到该 DEK 的 256 个 keyId，登记进内存哈希表 `map<4字节keyId, map<dek_hash, DEK>>`。`dek_hash = SHA256(DEK)[0:8]`，仅作内存表 value 键、用于区分同 keyId 格内的不同 DEK，**不落盘**。读取某块时用其 keyId 查表，得候选 DEK 集合（通常 1 个，跨 DEK 碰撞时少数个），再以 GCM-SIV tag 试解确证；试解全部失败视为该块解密失败（报告给上层）。索引**随解锁动态增长**，新 DEK 一到即建条目并立即可用，不要求一次性建全。
  - **定位粒度**：24 bit 哈希 + byte1 共 32 bit；跨 DEK 碰撞从 2 字节 keyId 的 1/256 降至 ~1/65536，命中格子里几乎总是单个候选 DEK，减少误试。每 DEK 仍只需 256 次预计算。哈希对象含 256 位 DEK，无法被廉价离线枚举。
  - **DEK 来源 = 文件夹 DEK 树（见 05）**：每个文件夹（group）绑一个 DEK，子文件夹 DEK 由父 DEK 包裹。任意密文块的 keyId 指向所属文件夹的 DEK——同一文件夹内条目共享其 DEK（一对多），不同文件夹各自独立。普通块负载**不新增 keyRef**，与哪个 DEK 配对完全由头部 keyId 决定。
  - **顶层 root DEK 的信封（区别于普通块）**：三个顶层 group 内的 root DEK 经 **KEK** 以 AES-256-GCM-SIV 包裹；文件夹 DEK 经**父 DEK**包裹。root DEK 头部 keyId 用 KEK 派生变体 `byte1(1B) ‖ SHA256(KEK‖byte1)[0:3]`，文件夹 DEK 用父 DEK 派生变体——解锁时从 KEK 起逐层试解，避免"要解 DEK 却需先有 DEK"的鸡生蛋。

- **nonce = 96 位（12B）随机**（混合熵源，见"熵混合"）：BC 的 AES-GCM-SIV 要求 12 字节 nonce（RFC 8452 推荐）；GCM-SIV 抗误用，碰撞只泄露"同明文同密文"的相等性；96 位随机碰撞概率可忽略。
- 结构化备选（不推荐，除非需要确定性 nonce）：`机器ID(32) ‖ 计数(64) ‖ 随机(32)`；**禁止时间戳入 nonce**——nonce 公开存于文件头，时间戳会泄露对象写入时间。
- **AES-256-GCM-SIV tag = 全量认证**：覆盖 ciphertext 与 **AAD**。**AAD = 整个信封头（`magic ‖ version ‖ flags ‖ uuid ‖ keyId ‖ nonce`）**——tag 覆盖信封全部信息 + 密文。任何头部字段（uuid/keyId/nonce/flags/version/magic）被篡改都会破坏 tag → 拒绝读取；防搬运到别的对象、防算法版本降级、防 keyId/nonce 被改。
- **明文块（manifest）全量认证**：明文块无 AEAD tag，靠负载内 `mac` 字段（见"文件夹 DEK 与 manifest 内容"），**mac 覆盖信封头（`magic‖version‖flags‖uuid`）‖ JSON 负载**——同样包含信封信息，篡改任何一部分即失效。
- **为何 16B**：128 位认证强度与系统整体安全等级（256 位密钥）一致；对伪造攻击单次尝试成功率 2⁻¹²⁸，继续加长无实际增益。
- 统一读写管线：读 → 反推 xorByte（`bytes[0]⊕magic[0]`）解异或 → 校验 magic/version → AEAD 解密验证 → 返回负载。
- 引擎层仍支持 codec==null 裸明文写（无信封、无验证），适配器当前不使用（见 04/05）；读取模式在引用处声明。

## 完整性设计（威胁模型：防混入/篡改）

威胁模型限定为"仓库中不允许出现伪造或被篡改的对象文件"（**不防整体回滚/重放**——那是 git 历史与远端背书范畴，超出本设计）：

1. **对象级验证（内联）**：任何非本应用生成、或内容被改动的文件，tag 验证失败即拒绝读取；AAD 绑定 key 路径，把文件挪到别的 key 下同样失败。
2. **manifest 验证**：解锁后以 KEK 派生密钥校验 manifest 的 MAC，防止伪造/篡改的 manifest（含降级，见"版本化算法适配层"）。

## KDF 参数

- **Argon2id 参数可配置**：创建/换主密码时可选档位，权衡速度与安全；参数存于 manifest，打开时以 manifest 为准（各仓库可不同，向后兼容）。
  - **默认高安全档**：memory ≥ 256 MiB、iterations ≥ 3、parallelism 4。这是密码管理器（高价值、可离线暴力）的推荐起点。
  - 允许降档（如资源受限设备）但默认不降、降档需显式选择并提示风险。
- 参数随 manifest 块保存，便于将来升级迁移；打开时以 manifest 为准。

## 文件夹 DEK 与 manifest 内容

**文件夹 DEK**（存于各 group 对象负载的 `dek` 字段，见 05；三个顶层 group 随机 uuid，各持 root DEK）：

- 三个顶层 root DEK：经 **KEK** 以 AES-256-GCM-SIV 包裹；普通对象树子文件夹 DEK 经**父 DEK**包裹。负载字段 = 被包裹的 DEK 密文。
- 每个文件夹一个 DEK；**换主密码 = 用新 KEK 重新包裹三个顶层 root 的 DEK**（普通对象树子文件夹 DEK 链不动）。
- 主密码正确性校验隐含在解密成败：三个 root DEK 的 GCM-SIV tag 验证通过 = KEK 正确。
- **不含** salt 与 KDF 参数（它们在 manifest；KDF 必须先于解锁执行）。

**manifest**（明文 + MAC，MAC 由解锁后 KEK 派生的验证密钥计算；按 04b 作为**明文 base58 块**存放，用负载 `type == "manifest"` 识别，负载为 JSON，无独立特殊文件）：

```json
{
  "version": 1,
  "type": "manifest",
  "cryptoVersion": "gcm-siv-1",
  "kdf": "argon2id",
  "salt": "<base64>",
  "params": { "m": 262144, "i": 3, "p": 4 },
  "warehouseTime": 1,
  "updateTimestamp": 1,
  "mac": "<base64>"
}
```

- `version`：JSON 结构版本；`type`：固定 `manifest`。
- `cryptoVersion`：算法套件版本，见"版本化算法适配层"。
- `kdf`/`salt`/`params`：KDF 参数（salt 创建时随机生成、终身不变），必须先于解锁生效。
- 可选：vault 创建时间。
- `mac`：**全量认证**——覆盖信封头（`magic‖version‖flags‖uuid`）与 JSON 负载全部内容（cryptoVersion/kdf/salt/params/warehouseTime/updateTimestamp/version/type），防篡改/降级。**MAC 密钥派生**：`macKey = HKDF-SHA256(KEK, info="sanctum-manifest-mac", 32B)`，对"信封头 ‖ 负载规范字节序"做 HMAC-SHA256。随主密码变化（KEK 变则 macKey 变），故换主密码须重算（见"换主密码"）。

## 仓库时间戳（全局写入锚点）

- manifest 内含**仓库时间戳 `warehouseTime`**（毫秒），是全局写入时间锚点，**初值 1**，**仅在关闭库时更新**（不每次写都动，保持局部性）。
- **每块写入时**（所有类型：manifest/group/entry/field/sshKey/icon），其 `updateTimestamp`（毫秒）= `max(两值)`：
  1. `(nanoTimeNow − 启动nanoTime) 毫秒 + warehouseTime`——相对锚点：会话内单调时钟时长 + 仓库锚点；
  2. `仓库中所有文件的最大 updateTimestamp`——保证不倒退。
- `nanoTime` 用单调时钟（`System.nanoTime`），不受系统改时间影响；存储单位毫秒。
- **用途**：同步冲突仲裁（`updateTimestamp` 大者 wins，见 06）。跨设备基于同一 `warehouseTime` 锚点，写入时间戳全局可比、单调。引导块（manifest）与密钥所在块（group）也带 `updateTimestamp`，但冲突仍走各自机制（keyId 定位 / MAC）。
- **同步操作前**：先更新 manifest（写入最新 `warehouseTime`，按同一 max 逻辑，重算 MAC）→ commit → 再与远端同步（见 06）。
- manifest 本身修改时间即仓库全局依据；`warehouseTime` 明文可见（非敏感）。

**解锁流程（惰性增量）**：
1. 扫描全部块，读出所有明文块（`flags(0x02)`）负载 JSON，按 `type == "manifest"` 找到 manifest（不依赖固定 UUID/文件名）。
2. 按 manifest 的 KDF 参数 + salt 派生 KEK，验 manifest MAC（防篡改/降级）。
3. 以已知密钥（初为 KEK）为**工作队列**，反复尝试解开队列能解开的块——解出三个顶层 group（root DEK）即得三个 root DEK，加入已知密钥集并入队继续；再沿普通对象树递归解出各子文件夹 DEK。密钥依赖可任意链式/嵌套（父 DEK 包子 DEK），无需预定顺序。
4. 每得一个 DEK 即时为其建立 keyId 索引条目（遍历 byte1 的 256 值）并立即用于后续查找——**索引的建立与使用交织进行，无"先全部建完再用完"的干净分界**。
5. 派生 encKey、构建内存目录（见 05）；普通块用其 keyId 查当前索引试解。

## 外部密钥加解密服务（外部密钥 = 字段 kind）

为外部软件提供"用库里密钥加解密数据"的能力。**不再有独立 extKey 类型**——外部密钥就是某个数据条目下的**自定义字段**，`kind = "externalKey"`，字段值即密钥材料（见 05）：

- **外部密钥**：某条目的自定义字段，`kind:"externalKey"`，值 = 密钥材料。它随条目加密存储、被条目引用即天然激活（GC 可达），无需特殊激活约束。
- **标识**：外部用该字段对象的 UUID 指定密钥（`list()` 返回激活的 externalKey 字段的 uuid + description）。
- **每个 externalKey 带描述**：字段的 `description`（或字段名）说明用途。

**接口**：
- `byte[] encrypt(byte[] data, UUID fieldUuid)` → 密文
  - 指定 externalKey 字段（UUID），取其密钥材料加密，返回密文。
- `byte[] decrypt(byte[] cipher)` → 明文
  - **外部不传 UUID**，靠密文块头自带的 `keyId` 定位解密密钥，经 **GCM-SIV tag 试解密**确证。
- `List<KeyInfo> list()` → 当前**可用**（`kind == "externalKey"` 且被引用激活）字段的 `uuid` + `描述`。

**隔离与防泄漏（关键）**：
- **解密候选域 = 仅 `kind == "externalKey"` 的字段密钥**。系统密钥（三个顶层 root DEK / 文件夹 DEK）的 keyId **不在**外部解密的候选里，外部即使传入"恰等于某文件夹 DEK keyId"的密文头，候选集中无系统 DEK → 试解失败 → 拒绝。**不会路由到系统密钥**。
- **加密指定 UUID 时**，只接受 `kind == "externalKey"` 的字段；指向系统对象/普通字段 → 拒绝。
- 外部密钥与系统密钥（文件夹 DEK）语义隔离：外部密钥只服务外部数据，系统 DEK 只加密库内对象。

### HTTP 传输（本地，JSON）

向外部程序通过**本地 HTTP + JSON** 暴露**外部密钥加解密服务**（仅此能力；不暴露任何编辑/读写仓库数据的接口）：

- **监听**：仅绑定 `127.0.0.1`（localhost），可用 JDK `com.sun.net.httpserver.HttpServer` 实现，零额外依赖。
- **范围**：仅 `/keys/list`、`/crypt/encrypt`、`/crypt/decrypt` 三个端点（外部密钥加解密）；**不提供** put/get/delete/编辑/仓库管理。
- **生命周期**：HTTP 服务**跟随应用启动**（始终监听端口）；**锁定时不提供服务**——接口保留、调用即返回错误（`locked`），不泄露任何密钥能力。
- **鉴权**：不鉴权；安全依赖"仅绑定 localhost + 本机信任模型"（见 03）。解不出/拒绝时统一返回失败，不区分"是否系统密钥"。
- **数据格式**：二进制数据用 base64，密文用 base58（与内部一致）；JSON 传参。

**端点**：

`POST /keys/list`
- 请求：`{}`
- 响应：`{ "ok": true, "keys": [{ "uuid", "name", "description" }] }`（激活 externalKey 字段列表）

`POST /crypt/encrypt`
- 请求：`{ "uuid": "<fieldUuid>", "data": "<base64 明文>" }`
- 响应：`{ "ok": true, "cipher": "<base58 密文>" }`

`POST /crypt/decrypt`
- 请求：`{ "cipher": "<base58 密文>" }`
- 响应：`{ "ok": true, "data": "<base64 明文>" }`

**错误响应**（统一）：
```json
{ "ok": false, "error": "<code>", "message": "<说明>" }
```
- 错误码：`locked`（锁定）/ `unknown_key` / `inactive_key` / `wrong_type` / `decrypt_failed` / `bad_request`。
- 锁定期间所有端点一律返回 `locked`。

## 防降级与完整性

- 文件头 magic + version，读取时校验，版本不符拒绝打开，防降级攻击。
- `manifest` 块（负载 `type == "manifest"`）记录格式版本、KDF 参数与 cryptoVersion，打开仓库时先校验；manifest 的完整性由解锁后 KEK 派生密钥的 MAC 保证（见"版本化算法适配层"）。

## TOTP

- TOTP 种子作为普通字段加密存储（见 05 密码库适配器）。
- 生成验证码用 Bouncy Castle HmacOTP（RFC 6238），无需服务端。
