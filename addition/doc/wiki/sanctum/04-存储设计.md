# 04 存储设计

## 设计目标

底层存储与业务数据结构解耦：schema 无关的对象库（key → 字节 + 读取模式），上层结构以适配器方式插入（见 05）。明文与密文共享**同一套存储管线**，唯一差异是编解码步骤；读取模式由引用方声明。

## 为什么不是内容哈希寻址

git 本身就是内容寻址的对象库：未变文件不重存、历史可回滚、冲突可检测。启用同步时 vault 根即 git 仓库，这些能力已经具备——在它之上再叠一层内容哈希等于**重复实现 git**。而且 SECRET 对象因随机 nonce 每次密文都不同，天然无法去重，内容寻址唯一确定的收益（明文去重）git 已提供；代价却是读路径多一跳（ref → 对象）、需要 GC、还要维护 refs 表自身的一致性。

**结论：路径寻址（确定性 key）对象库。** "局部修改→局部密文"是路径属性：每个逻辑单元占一个 key 的文件，改哪个动哪个；版本、去重、回滚（如启用 git）交给 git，否则交给用户自行备份。

## 底层：纯字节存储引擎（不负责密码学）

- 对象：key（调用方约定的字符串，如 `<uuid>`）→ 字节，物理统一存放于库根。
- **存储引擎不导入任何密码学**：不管加密、解密、密钥、magic 头；密钥管理（DEK/KEK/派生/生命周期）完全在 crypto 层（见 02），store 不持有任何密钥。
- 编解码由调用方**每次操作时注入**的 Codec 决定：

```java
public interface Codec {
    byte[] encode(byte[] data, long timestamp);   // 加密（或恒等）；timestamp 为块级时间戳（AAD）
    byte[] decode(byte[] data, long timestamp);   // 解密（或恒等）
}
```

- 写：`content = codec != null ? codec.encode(data, timestamp) : data` → 写文件。
- 读：读文件 → `codec != null ? codec.decode(bytes, timestamp) : bytes`。
- **不传 codec 即裸明文读写（无信封、无验证）**；传了由 codec 决定：CipherCodec 嗅探 magic 判别并解密验证（见 02）。
- **读取模式在引用处声明**：谁引用这个对象，谁在其内容中写明 `mode`（`raw` 直接读 / `cipher` 解密 / 未来可扩展）；引擎不感知，写时按模式选 codec，读时按模式取用。mode 即解码器选择器。
- 解锁 = 拿到 CipherCodec（外部构造）；锁定 = 丢弃引用，store 本身无状态可丢。
- 适配器统一使用 UUID 作 key；引擎对 key 无约束，其余操作（删、枚举、同步）共用同一套实现。

## 仓库布局

```
vault/                          -- 库根（可为普通文件夹，或 git 仓库根，见下）
├── <三个顶层 group 块>           -- 普通对象/icon/sshKey root（各持 root DEK，KEK 包裹，parent 为根概念 tag，见 02/05）
├── <manifest 块>                -- 格式版本、KDF 参数（明文块，type=manifest，parent=manifest，见 02/04b）
└── {xx}/                       -- uuid 无连字符 hex 前 2 字符（git 风格两层目录分片）
    └── {rest}.md               -- 一文件一块（UUID 命名，见 04b/05）
```

- 库**不强绑定 git**：普通文件夹即可用；是否 git、是否启用同步按 04b"库形态与 Git 关系"判定。启用同步时 vault 根即 git 仓库根。
- **两层目录分片**：对象文件按 uuid 前 2 字符分片到子目录，避免单目录文件爆炸（git 风格）；`独立仓库` 形态下这些目录位于 `data/` 内（见 04b）。
- **无独立特殊文件**：manifest 是明文 base58 块（负载 type=manifest），三个顶层 group（含 root DEK）与其余对象同构。
- 仓库内**无用户内容明文对象**（当前适配器除 manifest 明文引导块外全密文）；库根文件外观一致，外部无法区分明文/密文。

## 存储引擎接口（内部，不对外暴露）

`ObjectStore` 是 core **内部**的存储引擎接口，只供进程内上层（适配器/同步）调用，**不通过网络/HTTP 暴露**：

```java
public interface ObjectStore {
    byte[] get(UUID blockUuid, Codec codec);                 // codec == null 视为裸明文读取
    void put(UUID blockUuid, byte[] data, Codec codec, long timestamp); // 覆盖对应文件
    void delete(UUID blockUuid);                             // 物理删除对应文件
    List<UUID> list();
    List<Block> scan();
}
```

- 不感知上层结构；key（UUID）命名空间由适配器约定，路径由存储层按 uuid 前 2 字符分片派生。
- 本二进制引擎**无 GC**：覆盖即替换，历史由 git（启用同步时）管理。（markdown 变体 04b 提供显式 `gc()` 清理孤立块，属变体能力，见 04b。）
- 无 `commit`/`ChangeSet`：单块写即落盘，无提交语义；git 提交移入 app 侧 `SyncService`（见 06）。

## 明文与密文

- **读取模式在引用处声明**：引用方内容中写明 `mode`（写时决定 codec，读时按模式取用）；引擎层保留 codec==null 裸明文能力（无信封、无验证）。
- **约定**：用户内容一律 mode=cipher 并走 CipherCodec。
- **加密粒度 = 对象粒度**：改一个对象只覆盖一个文件（保持"明文局部修改→密文局部修改"）。

## key 与元数据泄露

key 即文件名（随机 UUID）：零信息量（不含任何用户命名、无明文/密文前缀）；字段名、条目名等用户命名**从不进入 key**（字段对象按 UUID 引用，见 05）。

**物理边界**：对象存在性、数量、大小仍可见。对策：密文 padding 到固定档位藏真实大小；结构信息（字段名/数量/归属）藏于加密的条目记录内（见 05）。

## 写路径与原子性

- 单 key：编解码（SECRET 加密）→ 写文件（创建目录 + 覆盖写；文件内容仅一行 `timestamp:base58`）。
- 一次写操作 = 一个对象文件的覆盖；对象间无跨文件原子性（崩溃中间态由 git 历史兜底，见 06）。
- 单进程内 ObjectStore 串行化写入。
