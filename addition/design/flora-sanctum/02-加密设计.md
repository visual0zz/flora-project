# 02 加密设计

## 密钥层次

```
master password
   └─ Argon2id (Bouncy Castle Argon2BytesGenerator) ─> KEK (256 bit)
        └─ 包裹随机 DEK（存于 vault/key.bin，换主密码只重写它）
             └─ HKDF-SHA256(DEK) 派生子密钥
                 ├─ encKey   → AES-256-GCM 加密 SECRET 对象载荷
                 ├─ blindKey → HMAC-SHA256 生成 key 中的名字寻址段（见 04）
                 └─ macKey   → HMAC-SHA256 验证 PLAIN 对象载荷（见下）
```

- KEK：由主密码经 Argon2id 派生，不落盘。
- DEK：打开仓库时随机生成（或首次创建），用 KEK 加密后写入 `key.bin`；仅在解锁期间驻留内存。
- 子密钥：encKey / blindKey / macKey 由 HKDF-SHA256 从 DEK 派生，遵循密钥分离（加密、寻址盲化、完整性验证互不共用）。
- 换主密码 = 只重写 `key.bin`，SECRET 对象不动，保持"局部修改"性质。

## 算法接口策略

- **标准算法走 JDK JCA 接口**（`javax.crypto`）：AES-GCM、HMAC-SHA256、SHA-256、密钥生成、SecureRandom；BC 以 Provider 形式注册在后备位（或默认 JDK 实现，AES-GCM 有 AES-NI 硬件加速）。代码只依赖标准接口，可移植、可换 provider。
- **JDK 没有的算法用 BC 原生接口**（`org.bouncycastle.crypto`）：Argon2id（`Argon2BytesGenerator`）JCA 无对应，必须 BC；HKDF 优先 BC（JDK 新版本 KDF API 可用则优先）。
- 结论：`bcprov` 依赖不可省，但业务代码尽量面向 JCA 编写，降低对 provider 的耦合。

## 版本化算法适配层

- `manifest` 记录 `cryptoVersion` 与 KDF 参数；SECRET 对象头部已有逐对象 `version` 字节（见下）。
- 适配层 = CodecRegistry（version → Codec 工厂）：
  - `Codec forRead(int version)`：按对象头部版本分发到对应实现，**旧仓库照常读（向后兼容）**；
  - `Codec latest()`：写路径永远用最新版本。
- 打开旧仓库：读用 manifest 记录的版本；首次写入自动把 manifest 升级到最新，之后新对象用新格式。
- **惰性迁移**：旧对象保持旧格式直到被再次写入（符合"局部修改"哲学）；另提供显式迁移命令批量重写。
- 发布新算法版本 = registry 注册新实现 + bump 版本；旧实现保留供读，不删除。
- **防降级**：manifest 为明文，必须附带完整性校验——解锁后以 KEK 派生的验证密钥校验其 MAC（覆盖 KDF 参数等全部内容），篡改则拒绝打开。

## 对外接口：Codec

crypto 层对外提供 Codec 实现（CipherCodec），供存储引擎**每次读写注入**（见 04）：

```java
public final class CipherCodec implements Codec {
    CipherCodec(SecretKey encKey, SecretKey blindKey);   // 解锁流程构造
    public byte[] encode(byte[] data);                   // 加密 + magic 头
    public byte[] decode(byte[] data);                   // 嗅探 magic 判别并解密
}
```

- 密钥管理（DEK/KEK/派生/生命周期）全在 crypto 层：解锁 = 构造 CipherCodec；锁定 = 丢弃引用。
- 存储引擎不感知密码学，不依赖 crypto（依赖反转，见 04）。

## 对象信封格式（完整性）

**验证码与内容同文件内联**：单文件原子写（temp + rename）保证内容与验证码不会撕裂；对象自包含、可自验，符合统一读写管线。分开存放无安全增益——验证码与内容同处一个存储域时，恶意储存方可一并改写；分开反而引入双文件一致性问题。

| 对象 | 字节布局 | 验证 |
|---|---|---|
| SECRET | `magic(4B) + version(1B) + flags(1B) + nonce(12B) + ciphertext + tag(16B)` | AES-GCM tag（AEAD，AAD = key 路径 + version + flags） |
| PLAIN | `magic(4B) + version(1B) + flags(1B) + payload + mac(16B)` | HMAC-SHA256(macKey, header‖payload) 前 16B |

- SECRET 的 GCM tag 本身就是验证码（认证加密），覆盖 ciphertext 与 AAD；**AAD 绑定 key 路径**，可发现"把对象密文搬运到别的 key"的篡改。
- **为何 SECRET 用 GCM tag、PLAIN 用 HMAC**：AES-GCM 是认证加密，tag 是加密的固有输出，密文天然自带验证码；明文未加密，才需显式附加 HMAC。并非两套签名方案，而是"加密自带的验证码"与"明文所需的验证码"。
- **为何 16B**：128 位认证强度与系统整体安全等级（256 位密钥）一致；对伪造攻击单次尝试成功率 2⁻¹²⁸，继续加长无实际增益。
- PLAIN 的 mac 由 macKey（DEK 派生）计算，储存方无密钥无法伪造。
- 统一读写管线：读 → 校验 magic/version → SECRET 走 AEAD 解密验证 / PLAIN 走 HMAC 验证 → 返回载荷。
- **豁免**：锁定态需读取、非敏感的展示对象（如自定义图标）可由 flags 标记为不验证——macKey 只在解锁后可用，锁定时无法验证；且其被篡改无安全影响。

## 完整性设计（威胁模型：防混入/篡改）

威胁模型限定为"仓库中不允许出现伪造或被篡改的对象文件"（**不防整体回滚/重放**——那是 git 历史与远端背书范畴，超出本设计）：

1. **对象级验证（内联）**：任何非本应用生成、或内容被改动的文件，tag/mac 验证失败即拒绝读取；AAD 绑定 key 路径，把文件挪到别的 key 下同样失败。
2. **manifest 验证**：解锁后以 KEK 派生密钥校验 manifest 的 MAC，防止伪造/篡改的 manifest（含降级，见"版本化算法适配层"）。
3. 豁免：锁定态需读的展示对象（图标等）不验证（见"对象信封格式"）。

## KDF 参数

- Argon2id 建议初始参数：memory 64 MiB、iterations 3、parallelism 4。
- 参数随 `vault/manifest` 保存，便于将来升级迁移；打开时以 manifest 为准。

## key.bin 与 manifest 内容

**key.bin**（密文文件，格式同 SECRET 信封）：

- 内容 = DEK（256 位随机）经 KEK 以 AES-GCM 加密：`magic + version + nonce + ciphertext(DEK) + tag`。
- 主密码正确性校验隐含在解密成败：GCM tag 验证通过 = KEK 正确。
- **不含** salt 与 KDF 参数（它们在 manifest；KDF 必须先于解锁执行）。

**manifest**（明文 + MAC，MAC 由解锁后 KEK 派生的验证密钥计算）：

- 格式 version；
- cryptoVersion（算法套件版本，见"版本化算法适配层"）；
- KDF：算法（Argon2id）+ salt（创建时随机生成、终身不变）+ 参数（memory/iterations/parallelism）；
- 可选：vault 创建时间。

**解锁流程**：读 manifest → 按其中 KDF 参数 + salt 派生 KEK → 验 manifest MAC（防篡改/降级）→ 解密 key.bin 得 DEK → 派生 encKey / blindKey / macKey。

## 防降级与完整性

- 文件头 magic + version，读取时校验，版本不符拒绝打开，防降级攻击。
- `vault/manifest` 记录格式版本、KDF 参数与 cryptoVersion，打开仓库时先校验；manifest 的完整性由解锁后 KEK 派生密钥的 MAC 保证（见"版本化算法适配层"）。

## TOTP

- TOTP 种子作为普通字段加密存储（见 05 密码库适配器）。
- 生成验证码用 Bouncy Castle HmacOTP（RFC 6238），无需服务端。
