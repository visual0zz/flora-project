# 04b Markdown 存储变体

> 本文是 04 存储设计 与 05 密码库适配器 的一个变体：把"底层对象库"具体化为"文件夹里的 markdown 文档集合"。
> 核心性质不变（明文局部修改 → 密文局部修改、局部提交、可合并并发、远端即备份），
> 差别在于**文件形态**：仓库就是一文件夹 markdown，**一文件恰好一个块**（内容为单行 `timestamp:base58`），
> 按 git 风格两层目录分片存放。
>
> **硬性外观约束**：三个顶层组（各含 root DEK）、组、口令条目、字段、SSH 密钥、图标——所有 markdown 文件在文件系统层面必须**看起来没有任何区别**。

## 为什么用 markdown

目标是让仓库**同时**是：

- 一个可被管理器正常读写、局部增量提交的密码库；
- 一堆用户可自行打开、阅读的普通 markdown 文档（内容为 `timestamp:base58`，无明文正文）。

管理器只读写自己约定的块，不依赖任何用户正文（当前实现不混排正文与密文，见"存储层语义"）。

## 存储层语义：一文件一块的 base58 集合

存储层**不感知文件的功能与负载语义**。它的世界只有两样东西：

- 一个 markdown 文件；
- 文件里的一个 **base58 块**。

**每个文件恰好一个块**（当前实现）：文件内容为单行 `{timestamp}:{base58}`，`base58` 解码 + 解异或后是标准信封字节。文件命名 = 对象 UUID（无连字符），按 git 风格两层目录分片：`{前2字符}/{剩余30字符}.md`。块是读写的最小单元。

- 不再支持"一个文件多个块"、"用户正文与密文交错"（旧格式兼容已去除）；扫描 = 遍历两层目录下的 `.md`，每个文件解析一个块。
- 块的识别靠块内自述的 **magic** 与 **uuid**；文件路径由 uuid 派生，**O(1) 定位**，无需全文扫描定位。

## 块自描述

每个 base58 块解码后是**自描述**的字节序列，**块本身就是单一的信封**。信封结构（见 02）：

```
magic(8B) + version(1B) + flags(1B) + uuid(16B) + keyId(4B) + nonce(12B) + ciphertext + tag(16B)
```

- **magic（8B）= `"Zhao zhi"` ASCII**：固定魔数，判明这是不是本应用的数据块。
- **随机字节异或混淆（不显式存 xorByte）**：整个信封字节序列与每块随机 xorByte 逐字节异或后落盘；xorByte 不落盘，读取时从落盘首字节反推（`xorByte = bytes[0] ⊕ magic[0]`）解异或、校验 magic（见 02）。每块落盘字节随机化，外部看不到固定 magic/内容模式。
- **flags 位标记**：`0x01`=密文 / `0x02`=明文。明文块负载为明文字节（无 keyId/nonce/tag），密文块负载为加密后的密文。
- **uuid（16B）**：本数据对象自己的 UUID。**AAD = 整个信封头（magic/version/flags/uuid/keyId/nonce）‖ 块级时间戳**，tag 覆盖信封全部信息 + 密文 + 时间戳，防密文被搬运到别的对象、防算法版本降级、防头部字段被篡改。
- **keyId（4B，仅密文）** = `byte1(1B) ‖ SHA256(DEK‖byte1)[0:3]`，byte1 逐块随机；解锁后用增量 keyId 索引定位候选 DEK，靠 GCM-SIV tag 试解确证（见 02）。
- **负载**：明文负载或密文。

明文块示例：`magic + version + flags(0x02) + uuid + plaintext`；密文块：`magic + version + flags(0x01) + uuid + keyId + nonce + ciphertext + tag`。两者由 flags 区分。

## 读写管线

**读（get / scan）**：
- `get(uuid)`：由 uuid 派生路径 `{前2字符}/{剩余30字符}.md`，读文件、解析 `timestamp:base58`、解异或、校验 magic → 得块。未找到返回 null。
- `scan()`：`Files.walk` 遍历两层目录下所有 `.md`，逐个解析为 `Block`（文件 + 行号=1 + 时间戳 + base58 + 原始字节 + 解异或字节）。损坏/不可识别文件跳过。
- 上层拿到块后各自解析：明文 → 直接读负载；密文 → 用 keyId 查索引、GCM-SIV tag 试解。

**写（put）**：编解码（若 codec 非 null）→ `{timestamp}:{base58}` 写文件（创建父目录、覆盖写）。每次写都是整文件覆盖——一文件一块，无需原位替换/重定位。

**新建**：与写相同——按新对象 UUID 派生路径创建文件。

**删除（delete）**：物理删除对应文件（一文件一块，无需软删除）。

## 孤立块：搜索与 GC

数据结构完整性由**更上层**保证（见 05）；底层不维护连通性。仓库中可能存在**无法连接到引用网络的孤立块**（条目删了但字段块还在、半写入的中间态）。上层提供显式 GC：

- **gc()（GarbageCollector）**：从根集合（manifest 明文块 + parent 为根概念 tag 的块）出发，沿归属边(parent)与引用边(icon/keyRef)遍历，不可达的孤立块删除并返回 uuid 列表。

**可达树（reachability）算法**：
- **根集合**：manifest 明文块（parent=manifest）；parent 为根概念 tag 的块（三个顶层 group 与用户顶层文件夹/条目、remote 字段）。
- **归属边（parent，层级，自下往上）**：group/entry/field/icon/sshKey → `parent`（父对象 uuid 或根概念 tag）。
- **引用边（非归属，仅可达性）**：group/entry → `icon`；remote（field kind）→ `keyRef`。
- **遍历**：队列从根出发沿归属边与引用边扩展；`孤立 = 全部块 − 可达`。

孤立块**无害**（git 历史兜底），gc 是显式、可审查的操作，不做自动清理。

## 上层：对象与互相指向

在块集合之上，上层把每个块分配给一个"数据对象"语义，所有对象互相**通过 UUID 指向**（详见 05）：

- 文件夹（组）、口令条目、条目内部的自定义字段、SSH 密钥、图标——都是对象，各占一个块。
- 每个数据对象在块内自述自己的 UUID；引用他人时写入对方 UUID。
- 对象语义（type、归属、字段映射）在**解密负载**里（全 JSON，见 05），不在 markdown 明文。
- 目录 = 解锁时扫描全部块、按解密负载的 type 分类、在内存构建引用图；锁定即丢弃，无持久索引。

## 文件夹 DEK（密钥树）

与 02 一致：落盘的是**用父密钥包裹的 DEK**。三个顶层 root 的 DEK 存于各自顶层 group（普通对象/icon/sshKey，随机 uuid、KEK 试解识别，用 KEK 包裹）；普通对象树子文件夹 DEK 存于各 group（用父 DEK 包裹），见 05。换主密码只重写三个顶层 group 的 DEK（新 KEK 重新包裹）+ 更新 manifest 的 MAC。

## manifest 块（明文块，外观与其余对象统一）

仓库必须有一条**明文**信息（KDF 参数 + salt + 算法版本）才能先生效 KEK 再去解锁——它不能放进密文块（解不开就死锁）。这条信息同样做成一个 base58 **块**，且是**明文块**（`flags(0x02)`），与其余对象同构、外观统一，没有独立特殊文件。

manifest 的明文 JSON 负载：

```json
{
  "version": 1,
  "type": "manifest",
  "cryptoVersion": "gcm-siv-1",
  "kdf": "argon2id",
  "salt": "<base64>",
  "params": { "m": 262144, "i": 3, "p": 4 },
  "updateTimestamp": 1,
  "mac": "<base64>"
}
```

- 负载统一为 JSON（含 `version`/`type`，与其余对象同构）。
- `cryptoVersion`：算法套件版本，见 02 版本化适配。
- `kdf`/`salt`/`params`：解锁前必须的 KDF 参数（派生 KEK）。
- `mac`：KEK 派生验证密钥算的 MAC，防篡改/降级。
- **如何识别它**：manifest 是**明文块**（`flags(0x02)`），解锁前即可 base58 解码直接读负载 JSON，看 `type == "manifest"` 判定——**不依赖固定 UUID、不依赖文件名**。扫描全部块，找到唯一的明文块且 type 为 manifest 者即取作 manifest。
- 明文 + MAC（同 02）：解锁后先验 MAC，篡改/降级则拒绝打开。

## 文件与目录布局

```
data/ (独立仓库) 或 库根 (普通仓库)
└── {xx}/                        -- uuid 无连字符 hex 前 2 字符（分片目录）
    └── {rest}.md                -- 一文件一块（uuid 剩余 30 字符，内容 timestamp:base58）
```

- 文件名**不承载语义**：管理器以块内自述的 UUID 为准，文件名由 uuid 派生（去连字符）。
- **两层目录分片**：前 2 字符作目录、其余作文件名（git 风格），避免单目录文件爆炸；uuid 前 2 字符（v4 第 1 字节 8 位）均匀分布（有测试验证）。
- **独立仓库**：上述结构位于仓库根的 `data/` 内；仓库根另有 `standalone.json`、`lib/`（全量 jar）与启动脚本（见下"库形态"）。

## 库形态与 Git 关系

**库不强绑定 git**：库就是一个普通文件夹，管理器随时可读写。git 是可选的外层，取决于该文件夹的实际处境：

- **普通仓库**：目录本身就是数据根（两层目录 + md 块），与独立仓库的 `data/` 内部结构一致。
- **独立仓库**：目录含 `standalone.json`（形态判定文件）+ `data/` + `lib/`（全量 jar）+ 启动脚本（跨平台双头脚本，依赖本地 JRE、git 可选）。应用从独立仓库内启动时，jar 检测自身同目录/工作目录的 `standalone.json` → 孤立形态，直接解锁该仓库。
- **文件夹在 git 仓库内，且基本只有 markdown 对象**（判定为"本应用的库"）：提供同步功能——用本地 git 自动 init 若缺、commit / pull --rebase / push 与远端同步（见 06）。

**形态判定（落 jar 内，不依赖脚本传参）**：
- jar 启动时检测**当前工作目录**与 **jar 所在目录**是否存在 `standalone.json`：存在 → 独立仓库形态；否则应用形态（进入历史仓库列表页）。
- 普通仓库/独立仓库的打开判定：目录含 `standalone.json` → 独立仓库（数据根为 `dir/data`）；目录下存在 md 块文件 → 普通仓库（数据根为目录本身）；否则非仓库。

**完全托管**：库根所有 markdown（含用户手动改动的）都纳入 commit/push/pull；管理器只读写自己的块，同步时把所有文件一起提交。
- 同步与否不影响**存储语义**：无论是否在 git 里，块识别、读写完全一致。
- 远端配置/密钥对象照常存为块（见 06），仅当启用同步时被读取用于本地 git。

## 局部性与提交

- 改一个块 = 只覆盖那一个文件，git 只见对应文件的一个局部 diff。
- 不启用 git 时，改动直接落盘，无 commit 概念（git 提交由 app 侧 SyncService 在启用同步时执行）。

## 一致性

- **底层不保证连通性**：块集合可能含孤立块，这是可接受状态。
- **完整性由上层维护**：上层以块内 UUID 构建引用图，损坏/缺失只影响该对象，目录可随时重建（见 05）。

## 限制与恢复

- **manifest 块丢失/损坏**：manifest 是明文引导块（负载 type=manifest）。若其文件被删或损坏，仓库失去 KDF 参数 + salt，**无法解锁**。恢复路径：用 git 历史（启用同步时）还原；未启用 git 时需用户从备份恢复。不提供"从密码重建 manifest"。
- **顶层 root group（DEK）丢失**：仓库无法解锁（对应 root DEK 遗失）。同理靠 git 历史/备份恢复。
- **单块大小上限**：一块 = 一个 base58 串，建议 ≤ 64 KB 原始字节（当前适配器全对象单块；大对象需扩展分块规则，暂未启用）。

## 隐私边界

- **对象块不可区分**：三个顶层 group、组、条目、字段、SSH 密钥、图标外观统一；是否密文、所属密钥组、是顶层组还是条目均不在明文可见（判定信息在块内）。
- **仍泄露的对象级信息**：仓库里存在若干长 base58 串、文件数量与大小。
- **字段名/条目名/归属关系安全**：只在解密负载内，markdown 明文不含任何用户命名。
