# 04b Markdown 存储变体

> 本文是 04 存储设计 与 05 密码库适配器 的一个变体：把"底层对象库"具体化为"文件夹里的 markdown 文档集合"。
> 核心性质不变（明文局部修改 → 密文局部修改、局部提交、可合并并发、远端即备份），
> 差别在于**文件形态**：仓库就是一文件夹 markdown，管理器把它们当作 **base58 块的集合**来读写。
>
> **硬性外观约束**：主密钥文件、组、口令条目、自定义字段、远端配置、图标——所有 markdown 文件在文件系统层面必须**看起来没有任何区别**。

## 为什么用 markdown

不是伪装。目标是让仓库**同时**是：

- 一个可被管理器正常读写、局部增量提交的密码库；
- 一堆用户可自行打开、阅读、甚至改写的普通 markdown 文档。

用户能看到的正文（说明、备注、组织笔记）是明文、可自由编辑；管理器只读写自己约定的 base58 块，其余一律忽略。这样"写文档"和"记密码"共存于同一套文件里，用户不必在两种形态间搬运。

## 存储层语义：base58 块的集合

存储层**不感知文件的功能、也不感知文件内的分块语义**。它的世界只有两样东西：

- 一个 markdown 文件；
- 文件里散布的若干 **base58 块**。

管理器把仓库看成一张 **base58 块集合**，块是读写的最小单元。上层的所有处理（哪些是明文/密文/文件夹/条目/自定义字段）都针对**块**进行，与"块存在哪个文件、文件里还有没有别的内容"无关。

**块没有固定边界标记**。管理器对仓库里**任意一段看起来像 base58 的字符串**都尝试 base58 解码，解码后看前几个字节是不是本应用的 **magic number**——是则确认为一个数据块，否则当作普通文本忽略。

```
一个 markdown 文件里，任何位置都可能埋着数据块（无显式标记）：

# 我的服务器笔记

正文随意，一个长串可能就是一块：8f3TQxD2nX4YzRq9pW7cBvKmJh5LgEwUaFdGsN1t...

中间再放一点，两段之间不需要任何特殊标签。
```

- **块候选 = 连续的一串 base58 字符**（base58 字母表 `123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz`，不含易混淆的 0/O/l/I）。管理器用扫描器把文本切成候选串，逐个尝试。
- **识别靠 magic，不靠标签**：候选串 base58 解码后，头部校验 magic（固定字节序列）匹配才认定为数据块。用户正文里的任意长串、甚至误写的类 base58 串，magic 不匹配即被忽略，不可能被误读。
- **一个文件可有零个或多个块**；块可以相邻、可以相隔任意 markdown，没有定位标签。
- 管理器**不关心**某个块在哪个文件、文件是做什么的；上层只消费"块列表"。

## 块自描述

每个 base58 块解码后是**自描述**的字节序列，**块本身就是单一的信封**（没有"外层块 + 内层信封"两层）。信封结构（见 02）：

```
magic(4B) + version(1B) + flags(1B) + uuid(16B) + keyId(2B) + nonce(16B) + ciphertext + tag(16B)
```

- **magic**：判明这是不是本应用的数据块（避免把用户乱写的 base58 当数据）。
- **flags 位标记**：`0x01`=密文 / `0x02`=明文。明文块载荷为明文字节（无 keyId/nonce/tag），密文块载荷为加密后的密文（见下）。
- **uuid（16B）**：本数据对象自己的 UUID（见"上层：对象与互相指向"），同时作为 AEAD 的 AAD 绑定，防密文被搬运到别的对象。
- **keyId（2B，仅密文）** = SHA256(KEK) 前 2 字节，供候选定位，靠 GCM-SIV tag 试解确证（见 02）。
- **负载**：明文载荷或密文。

明文块示例：`magic + version + flags(0x02) + uuid + plaintext`；密文块：`magic + version + flags(0x01) + uuid + keyId + nonce + ciphertext + tag`。两者由 flags 区分，无需明文标注。

存储层**不解释**这些含义，只负责：识别块边界、读出原始字节、把新字节写回同一位置。判读（是密文/明文、是条目/字段）由上层完成。

## 读写管线

**读**：遍历全部 markdown 文件 → 扫描每处"像 base58 的连续串" → 逐个 base58 解码 + magic 校验 → 得一批数据块（可能含明文、密文、或用户误写的无效串）。上层拿到块列表后各自解析：
- magic 不匹配 → 视为用户正文干扰，跳过；
- 是密文 → 用信封内 keyId 挑候选密钥、tag 试解；
- 是明文 → 直接读负载。

**写（原位替换）**：要更新某块时，**写前重新定位一次**，再原位替换：
- 内存维护一张表：记录每个块是从哪个文件的**哪一行**读到的（读取时填充）。
- 写回时，**从记录的那一行出发，向两侧重新定位**当前该块的位置（优先找离记录行最近的有效块；按 uuid 确认是本对象）。
- 在找到的位置用新 base58 串替换旧串；若找不到或出现歧义（该位置已无有效块、或同 uuid 多处）则**中止并提示**，绝不盲目写入。
- 其余文件、其余块、用户正文一律不动 → 局部修改只引起局部密文/明文变化。

**为什么不做临时文件/快照替换**：写回本身只改一个串，不重写整个文件；写前重定位即可确认落点。无 temp + rename、无"先比对快照再写"的整文件流程——减少文件系统操作，也避免竞态下整文件互相覆盖。

**重定位失效的情形**（用户改了正文导致记录行不再有效）：记录行上下已无匹配的 uuid 块、或被拆行/改动 → 中止写入并提示，不猜测落点。块的识别与写回全程以 uuid 为准，不依赖"原串仍在原处"。

**新建**：没有对应旧块时，新建一个 markdown 文件，内部只需一句简单说明 + 一个 base58 串即可。文件标题、正文可任写，不影响管理。

**去重**：同一数据若在多个位置存在副本（用户手抄、多块），只需修改其中一处——上层以 UUID 为准，块间彼此独立，改哪个都是有效的新版本（见"一致性"）。

## 孤立块：搜索与 GC

数据结构的完整性由**更上层**保证（见"一致性"）；底层不维护任何连通性。因此仓库中可能存在**无法连接到整个引用网络的孤立块**（条目删了但字段块还在、用户残留的副本、半写入的中间态）。底层为此提供两个能力：

- **search(块)**：按 UUID / 内容特征在所有块中查找——定位某个对象当前的所有副本（去重、恢复、核查）。
- **gc()**：扫描全部块，解析引用关系，把不连入任何对象的孤立块列入清单，由上层确认后删除。删除只移除对应块的 base58 串（若文件因此只剩空骨架，可一并清理，但这是文件层优化，非必需）。

孤立块**无害**（git 历史兜底），gc 是显式、可审查的操作，不做自动清理。

## 上层：对象与互相指向

在块集合之上，上层把每个块分配给一个"数据对象"语义，所有对象互相**通过 UUID 指向**：

- 文件夹（组）、口令条目、条目内部的自定义字段、主密钥包裹、远端配置、图标——都是对象，各占一个（或几个）块。
- **每个数据对象在块内自述自己的 UUID**；引用他人时写入对方 UUID（如条目记录里字段名 → 字段对象 UUID 的映射，见 05）。
- 对象语义（type、归属、字段映射）在**解密负载**里，不在 markdown 明文；字段名/条目名/归属从不进入明文。
- 目录 = 解锁时扫描全部块、按解密负载的 type 分类、在内存构建引用图；锁定即丢弃，无持久索引。

## 主密钥块

与 02 一致，落盘的是**用主密码派生的 KEK 包裹的 DEK**（key.bin 的角色），**不是主密码本身**。它也是一个普通块，外观与其余对象无差别；换主密码只改写这个块。

## manifest.md（唯一特殊文件）

唯一的例外：仓库必须有明文信息（KDF 参数 + salt）才能先生效 KEK 再去解锁，所以 manifest 必须是明文。它不属于块/对象空间，是仓库根的基础设施文件：

```markdown
# vault manifest (do not edit)

**sanctum-format**: `1`

**sanctum-crypto**: `gcm-siv-1`        <!-- 算法套件版本，见 02 版本化适配 -->

**sanctum-kdf**: `argon2id`

**sanctum-salt**: `<base58>`

**sanctum-params**: `m=64MiB,i=3,p=4`

**sanctum-mac**: `<base58>`            <!-- KEK 派生验证密钥算的 MAC，防篡改/降级 -->
```

- 明文 + MAC（同 02）：解锁后先验 MAC，篡改/降级则拒绝打开。
- 解锁流程：读 manifest → 按 KDF 参数 + salt 派生 KEK → 验 MAC → 解出主密钥块的 DEK → 派生 encKey。
- manifest 与对象文件外观不同（有 `sanctum-format` 等），这是设计取舍：manifest 是仓库根明文基础设施，而**所有对象块（含主密钥）外观统一**。

## 文件与目录布局

```
vault/
├── manifest.md                      -- 仓库元数据（唯一特殊文件）
└── data/
    ├── <uuid>.md                    -- 可含一个或多个块；外观统一
    ├── <uuid>.md
    └── …
```

- 文件名**不承载语义**：管理器以块内自述的 UUID 为准，不依赖文件名（可以是随机 UUID，也可用户起名；后者会暴露条目名，见"隐私边界"）。
- 上层约定一个物理目录 `data/` 存放对象文件，纯属组织便利；存储层本身不依赖目录结构，扫描整个仓库根即可。

## 局部性与提交

- 完全沿用 04/06：改一个块 = 只替换那一处 base58 串，git 只见对应文件的一个局部 diff；一次 ChangeSet 一个 commit。
- 用户手改某文档正文 → 仅该文件在 git diff 中变化；只要不改块本身，管理器下次读取不受影响。

## 一致性

- **底层不保证连通性**：块集合可能含孤立块、重复块，这是可接受状态。
- **完整性由上层维护**：上层以块内 UUID 构建引用图，损坏/缺失只影响该对象，目录可随时重建（见 05）。
- **重复块**：上层以 UUID 识别"同一对象"，任意一个副本被更新都视为新版本；gc 可收敛冗余。

## 隐私边界（相对二进制方案的取舍）

- **对象块不可区分**：主密钥、组、条目、字段、远端配置、图标外观统一；是否密文、所属密钥组、是主密钥还是条目均不在明文可见（判定信息在块内）。
- **仍泄露的对象级信息**：仓库里存在若干长 base58 串、文件数量与大小。若这些不可接受，应退回 02/04 纯二进制信封（连 markdown 明文结构都不存在）。
- **字段名/条目名/归属关系安全**：只在解密负载内，markdown 明文不含任何用户命名。
