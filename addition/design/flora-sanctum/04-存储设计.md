# 04 存储设计

## 设计目标

底层存储与业务数据结构解耦：schema 无关的对象库（key → 字节 + 可见性），上层结构以适配器方式插入（见 05）。明文与密文共享**同一套存储管线**，唯一差异是编解码步骤；可见性是对象的固有属性。

## 为什么不是内容哈希寻址

git 本身就是内容寻址的对象库：未变文件不重存、历史可回滚、冲突可检测。vault 整个目录就是 git 仓库（见 06），这些能力已经具备——在它之上再叠一层内容哈希等于**重复实现 git**。而且 SECRET 对象因随机 nonce 每次密文都不同，天然无法去重，内容寻址唯一确定的收益（明文去重）git 已提供；代价却是读路径多一跳（ref → 对象）、需要 GC、还要维护 refs 表自身的一致性。

**结论：路径寻址（确定性 key）对象库。** "局部修改→局部密文"是路径属性：每个逻辑单元占一个 key 的文件，改哪个动哪个；版本、去重、回滚全部交给 git。

## 底层：纯字节存储引擎（不负责密码学）

- 对象：key（调用方约定的字符串，如 `plain/<uuid>`、`secret/<uuid>`）→ 字节。
- **存储引擎不导入任何密码学**：不管加密、解密、密钥、magic 头；密钥管理（DEK/KEK/派生/生命周期）完全在 crypto 层（见 02），store 不持有任何密钥。
- 编解码由调用方**每次操作时注入**的 Codec 决定：

```java
public interface Codec {
    byte[] encode(byte[] data);   // 加密（或恒等）
    byte[] decode(byte[] data);   // 解密（或恒等）
}
```

- 写：`content = codec != null ? codec.encode(data) : data` → 原子写。
- 读：读文件 → `codec != null ? codec.decode(bytes) : bytes`。
- **不传 codec 即明文读写**；传了由 codec 决定（CipherCodec 嗅探 magic 判别，见 02）。
- 解锁 = 拿到 CipherCodec（外部构造）；锁定 = 丢弃引用，store 本身无状态可丢。
- key 统一为 `plain/` 或 `secret/` 前缀 + 随机 UUID：两条路径除前缀与编解码外零差异，其余操作（删、枚举、提交、冲突、同步）共用同一套实现。

## 仓库布局

```
vault/                          -- Git 仓库根
├── key.bin                     -- DEK（SECRET 对象加密用，见 02）
├── manifest                    -- 格式版本、KDF 参数
├── plain/                      -- PLAIN 对象（UUID 命名）
└── secret/                     -- SECRET 对象（UUID 命名，内容带加密头）
```

plain/ 与 secret/ 仅是落盘目录不同，其余（命名、布局、操作、工具）完全一致。

## 对外 API

```java
public interface ObjectStore {
    void put(String key, byte[] data, Codec codec);    // codec == null 视为明文
    byte[] get(String key, Codec codec);
    void delete(String key);
    List<String> list(String prefix);
    CommitId commit(ChangeSet changes, String message); // 原子：一组 put/delete 一次提交
}
```

- 不感知上层结构；key 命名空间由适配器约定。
- 无 GC：覆盖即替换，历史由 git 管理。

## 明文与密文

- **明文** = 不传 codec（或恒等 codec）；**密文** = CipherCodec（crypto 层实现）。
- 物理分离（plain/ 与 secret/）由调用方 key 约定（`plain/<uuid>` vs `secret/<uuid>`），store 一视同仁。
- **约定**：用户内容默认走 CipherCodec；非敏感数据（图标等）不传 codec。
- **加密粒度 = 对象粒度**：改一个对象只覆盖一个文件（保持"明文局部修改→密文局部修改"）。

## key 与元数据泄露

key 为 `plain/` 或 `secret/` 前缀 + 随机 UUID：除目录前缀外零信息量（不含任何用户命名）。仅字段级拆分模式（见 05）下，自定义字段名需要可推导寻址，对策：

1. **HMAC 盲化**：`HMAC(blindKey, 条目id:字段名)` 前 16 hex（blindKey 见 02）。防离线字典攻击、防跨条目等值关联；解锁时可确定性重算。
2. **终极方案：随机 key + 加密映射**：字段文件用随机 key 寻址，name→key 映射存于加密记录，读多一跳。

**物理边界**：对象存在性、数量、大小仍可见。对策：密文 padding 到固定档位藏真实大小；整条打包藏内部结构（见 05）。

## 写路径与原子性

- 单 key：编解码（SECRET 加密）→ `.tmp-*` → 原子 rename → 一次 commit。
- 多 key：全部落盘后，一个 ChangeSet 一个 commit；崩溃中间态由 git 历史兜底，不对外暴露半更新。
- 单进程内 ObjectStore 串行化写入。
