# 图像模型嵌入文本模型的机制对比：LLM-AIO-Gateway 与 openhanako

> 日期：2026-08-09
> 范围：剖析 `absent/otherprojects/LLM-AIO-Gateway`（Python 网关）与 `absent/otherprojects/openhanako`（Node.js/TS 个人 AI Agent）两个外部项目如何将图像（多模态视觉）嵌入到文本模型对话中，并评估 openhanako 相对 Pi SDK 的自主功能占比
> 关联：`explore20260809-openhanako基座能力评估.md`（侧重 flora-root 复刻所需的通用能力，本文侧重图像嵌入机制与项目架构定位）

---

## 一、核心结论

- **LLM-AIO-Gateway**：网关架构，自己做完整的解析、归一化、路由与下游格式转换。图像嵌入有**两条机制**——原生视觉透传 + 视觉预处理器注入（用独立视觉模型把图片"翻译"成文字喂给纯文本模型）。
- **openhanako**：薄透传。自身只做 base64 统一编码与能力标记，真正的多模态组装发生在 Pi SDK（`@mariozechner/pi-coding-agent`）内部。但 openhanako **不是 Pi 的薄壳**——Pi 只被用在"会话执行 + 模型注册"两个点，外围产品能力（记忆、人格、沙盒、多平台桥接、桌面端）约占总代码 90% 以上。

---

## 二、LLM-AIO-Gateway（Python，网关架构）

管道：`入口协议(Ingress) → IR 中间表示 → Policy(视觉预处理+路由) → 下游 Adapter/Upstream`

### 2.1 请求解析与格式归一化

- 入口路由 `app/router/proxy.py`（`/chat/completions` L2610、`/v1/messages`、`/v1/responses`）经 `app/protocols/ingress.py` 转为 `InternalRequest`。
- 图像字段读取在 `app/protocols/ir.py`：
  - `_parts_from_openai_content`(L178)：识别 `image_url`/`input_image`/`image`/`file` 类型的 content part（L200）；
  - `_parts_from_responses_content`(L211)：识别 `input_image`（L230）；
  - `_anthropic_content_to_parts`(L294)：识别 Anthropic `type:"image"` 块（L313）；
  - 纯文本内嵌 data URI 由 `app/core/images.py::extract_image_data_uris`(L12) 提取。
- 核心归一化函数 `ir.py::_coerce_image_source`(L111)：统一处理 `image_url`(dict/str)、`url`/`uri`、`source`(str/dict)、`image`、`data`/`base64`/`file_data`，产出 IR source `{kind:"url"|"base64", media_type, data/url, detail}`。
- `images.py::normalize_image_content`(L23) 将文本内嵌 `data:image/...;base64,...` 转为 `image_url` content part。
- 归一化后为 `InternalPart(kind="image")`（`app/core/types.py::image_part` L48）。

### 2.2 嵌入文本模型的两条机制（核心）

1. **原生视觉透传**：模型被判定支持视觉时，图像 IR 直接经下游格式转换转发。
   - 能力判定 `_model_supports_native_vision`(proxy.py L2577) 按模型名含 `gpt-4o`/`claude-3`/`gemini`/`qwen-vl` 等启发式判断；liteLLM 注册时写入 `litellm.model_cost[...]={"supports_vision": True}`（`lite_llm.py` L141-144）。
   - `/models` 列表通过 `_model_should_advertise_vision`(L2607) 打上 `supports_vision`/`image_support`/`multimodal` 标记（L2568-2571），提示 Codex/OpenCode 等客户端发送图像块。
2. **视觉预处理器注入（Vision Model Injection）**：非多模态文本模型配置 `preprocessor` 后，`_policy_preprocess_request`(proxy.py L2234) → `preprocess_messages`(preprocessing.py L137) → `describe_image`(L48) 调用**另一个独立的视觉模型**，把每张图转成 `[Image #N]: <描述>` 文本替换原图，只喂文本给目标模型。仅当目标不支持原生视觉且配置了预处理器时才走此路径（`_internal_for_target_attempt` proxy.py L1497-1508）。

### 2.3 下游格式适配

| 下游 | 转换 | 位置 |
|---|---|---|
| OpenAI | `image_url`，base64 重编码为 `data:{media};base64,...` | `ir.py::_parts_to_openai_content`(L69-93, L88) |
| Anthropic | `{type:"image", source:{type:"base64", media_type, data}}`；URL 图片降级为文本 `[image URL: ...]` | `_append_anthropic_image_content`(L32-49) |
| Gemini | 无专用 adapter，经 liteLLM 转发（`image_url`→`inlineData`/`fileData` 由 liteLLM 完成） | — |
| Responses 原生端点 | 直接透传原始 body | `responses.py::native_responses_body`(L77) |

### 2.4 图像大小处理

- 输入侧无像素压缩；含图请求自动抬高 `max_tokens`（`min_image_max_tokens`，lite_llm.py L81/L223）。
- 预处理器有 `max_images` 上限（preprocessing.py L179）与描述缓存（L26）。
- 生成图像结果有 JPEG 缩略图压缩（`image_results.py::image_preview_data_uri` L73-114，PIL thumbnail + 质量递减循环）。

## 三、openhanako（Node.js/TS，薄透传 + 厚外围）

### 3.1 图像嵌入机制

统一图片对象：`{ type:'image', data: base64, mimeType }`。

- **粘贴**：`desktop/src/react/components/InputArea.tsx:254-280` `handlePaste` → FileReader → 正则 `data:(image/[^;]+);base64,(.+)` 拆出 mimeType+base64。
- **本地文件**：`handleSend`(L303-396) 分离图片/非图片附件；图片若非内联 base64 则 `hana.readFileBase64(path)`（Electron IPC，`desktop/main.cjs:1774-1782`）；非图片降级为 `[附件] path` 文本。
- **WS 校验**：`server/routes/chat.js:431-451` — 限 10 张、仅 png/jpeg/gif/webp、单张 ≤20MB base64。
- **透传链**：`chat.js:467` → `hub.send(text,{images})` → `hub/index.js:118` → `engine.prompt`(engine.js:204) → `core/session-coordinator.js:180-181`：`session.prompt(text, { images })`。
- **能力声明**：`~/.hanako/models.json` 模型 `input: ["text","image"]` 字段，默认生成在 `core/sync-favorites.js:36-42`。框架不做能力判断，依赖 Pi SDK 的 ModelRegistry 按 `input` 静默过滤图片（commit `165d51b` 注释）。
- **无**下载、压缩、token 估算逻辑；OpenAI/Anthropic/Gemini 格式转换全部在 Pi SDK 内完成，仓库内不可见。

### 3.2 Pi SDK 实际使用范围（薄的部分）

直接引用 Pi 的仅 8 处：

- **会话执行**：`createAgentSession`/`SessionManager`（`core/session-coordinator.js`、`hub/agent-executor.js`）——对话经 `session.prompt(text, {images})` 委托。
- **模型基础设施**：`AuthStorage`/`ModelRegistry`（`core/model-manager.js`）——models.json 注册表与凭证存储。
- **内置工具基座**：codingTools + createRead/Write/Edit/Bash/Grep/Find/LsTool（`core/engine.js`、`lib/sandbox/index.js`）——仅作底层工具，外面包了自研沙盒。
- **辅助**：`DefaultResourceLoader`（已禁掉其 prompt 模板并 override getSystemPrompt/getSkills）、`formatSkillsForPrompt`、`registerOAuthProvider`。

### 3.3 自主实现的部分（厚的部分）

| 方向 | 内容 | 位置 |
|---|---|---|
| 记忆系统（最大自研块） | SQLite FTS5 事实库（含 PII 清洗）、每 6 轮滚动摘要调度器、today/week/longterm/facts 编译、deep-memory、experience-extractor | `lib/memory/` |
| 多 agent/多平台协作 | hub 消息调度（channel-router/dm-router/guest-handler/scheduler/agent-executor）；Telegram/飞书/QQ 三套 adapter（含 BlockChunker 流式多气泡） | `hub/`、`lib/bridge/` |
| 工具系统（17 个自研） | browser（自研，走 Electron WebContentsView 而非 Playwright）、web_search、web_fetch、todo、cron、delegate、ask_agent、artifact、install_skill、pinned_memory 等 | `lib/tools/` |
| 安全沙盒 | macOS seatbelt / Linux bwrap OS 级沙盒 + PathGuard + tool-wrapper | `lib/sandbox/` |
| 人格与 Prompt | identity/yuan/ishiki 三层人格模板，4 套人格（Hanako/Butter/Ming/Kong）；override Pi 的 getSystemPrompt | `core/agent.js`、`lib/identity-templates/` |
| 工程外壳 | Fastify HTTP+WS（17 路由、token 鉴权、流式 `<mood>/<xing>` 标签解析、断点续传）；Electron 主进程 + React 前端（约 1.7 万行） | `server/`、`desktop/` |
| 自研 LLM 客户端 | 直连 OpenAI/Anthropic/Responses 三协议，绕过 Pi SDK，用于标题摘要、记忆编译、翻译 | `lib/llm/provider-client.js` |

代码量：`core`+`hub`+`lib`+`server` 约 2.2 万行自研 JS，desktop 约 1.7 万行。**抽掉 Pi SDK 后仍是一个完整的本地 agent 运行时。**

## 四、对比表

| | LLM-AIO-Gateway | openhanako |
|---|---|---|
| 语言/架构 | Python，网关 | Node.js/TS，本地 agent |
| 图像嵌入方式 | ①原生视觉透传 ②独立视觉模型生成文字描述替换图片 | 只透传 `{type:'image', data, mimeType}` 给 Pi SDK |
| 格式转换层 | 自研（OpenAI/Anthropic/Responses 三适配器） | Pi SDK 内部完成，项目不可见 |
| 能力判断 | 模型名启发式 + liteLLM 注册 | models.json `input` 字段 + Pi SDK 静默过滤 |
| 图像处理 | max_tokens 抬升、max_images 限制、描述缓存 | 仅 20MB/10 张校验 |
| 对底层 SDK 的依赖 | 无（全自研，可选 liteLLM） | 薄（仅会话执行 + 模型注册），外围 90% 自研 |

## 五、参考价值

1. **"图像嵌入文本"存在两种产品形态**：网关侧（LLM-AIO-Gateway）主动归一化/转换/降级，适合作为中间层；客户端侧（openhanako）统一编码后交给 SDK，适合快速集成。
2. **视觉预处理器注入**（用独立视觉模型把图片转文字再喂纯文本模型）是网关特有思路，对 flora-root 若实现 AI 网关类中间件有直接参考价值；flora-root 已有 `com.flora.ai.api` 多 provider 客户端，可在此基础上补"能力声明 + 图像格式归一化 + 视觉降级描述"三件套。
3. **openhanako 的价值不在多模态**，而在记忆/人格/沙盒/多平台桥接等外围；其"薄内核 + 厚外围"的架构边界（把 provider 差异隔离在 SDK 内）值得 flora 复刻时借鉴——对外部依赖只保留一个可替换的内核接口。
