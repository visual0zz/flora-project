# 04 存储设计

> 本文合并原「04 存储设计」与「04b Markdown 存储变体」：项目实际存储只有一种实现——文件夹里的 markdown 文档集合，
> 一文件恰好一个块（内容为单行 `timestamp:base58`），按 git 风格两层目录分片。底层对象库与具体文件形态不再拆分为两篇。

## 设计目标

底层存储与业务数据结构解耦：schema 无关的对象库（key → 字节），上层结构以适配器方式插入（见 05）。明文与密文共享**同一套存储管线**，唯一差异是编解码步骤。

**硬性外观约束**：根对象、组、口令条目、字段、SSH 密钥、图标、远端配置——所有 markdown 文件在文件系统层面必须**看起来没有任何区别**。

## 为什么不是内容哈希寻址

git 本身就是内容寻址的对象库：未变文件不重存、历史可回滚、冲突可检测。启用同步时库根即 git 仓库，这些能力已经具备——在它之上再叠一层内容哈希等于**重复实现 git**。而且密文对象因随机 nonce 每次密文都不同，天然无法去重，内容寻址唯一确定的收益（明文去重）git 已提供；代价却是读路径多一跳（ref → 对象）、需要 GC、还要维护 refs 表自身的一致性。

**结论：路径寻址（确定性 key）对象库。** "局部修改→局部密文"是路径属性：每个逻辑单元占一个 key 的文件，改哪个动哪个；版本、去重、回滚（如启用 git）交给 git，否则交给用户自行备份。

## 底层：纯字节存储引擎（不负责密码学）

- 对象：key（UUID）→ 字节，物理统一存放于库根的两层目录（见"仓库布局"）。
- **存储引擎不导入任何密码学**：不管加密、解密、密钥、magic 头；密钥管理（DEK/KEK/派生/生命周期）完全在 crypto 层（见 02），store 不持有任何密钥。
- 编解码由调用方**每次操作时注入**的 Codec 决定：

```java
public interface Codec {
    byte[] encode(byte[] data, String timestamp); // 加密（或恒等）；timestamp 为块级时间戳规范字符串（落盘前缀原文，AAD）
    byte[] decode(byte[] data, String timestamp); // 解密（或恒等）
}
```

- 写：`content = codec != null ? codec.encode(data, timestamp) : data` → 写文件。
- 读：读文件 → `codec != null ? codec.decode(bytes, timestamp) : bytes`。
- **不传 codec 即裸明文读写（无信封、无验证）**；传了由 codec 决定：CipherCodec 嗅探 magic 判别并解密验证（见 02）。
- 解锁 = 拿到加密能力（`TreeContext` 持 `Vault`，写路径统一构造 `CipherCodec`，见 05）；锁定 = 丢弃引用，store 本身无状态可丢。
- **当前适配器全库密文（除 manifest 明文引导块）**：读写路径统一走 CipherCodec，不存在按引用声明明/密读取模式的分支（旧设计"mode 在引用处声明"已随适配器收敛而移除）。

## 文件形态：一文件一块的 base58 集合

存储层**不感知文件的功能与负载语义**。它的世界只有两样东西：

- 一个 markdown 文件；
- 文件里的一个 **base58 块**。

**每个文件恰好一个块**：文件内容为单行 `{timestamp}:{base58}`，`base58` 解码 + 解异或后是标准信封字节。文件命名 = 对象 UUID（无连字符），按 git 风格两层目录分片：`{前2字符}/{剩余30字符}.md`。块是读写的最小单元。

- **不再支持"一个文件多个块"、"用户正文与密文交错"**（旧格式兼容已去除）；扫描 = 遍历两层目录下的 `.md`，每个文件解析一个块。
- 块的识别靠块内自述的 **magic** 与 **uuid**；文件路径由 uuid 派生，**O(1) 定位**，无需全文扫描定位。
- 文件名**不承载语义**：管理器以块内自述的 UUID 为准，文件名由 uuid 派生（去连字符）。

## 块自描述：信封格式

每个 base58 块解码后是**自描述**的字节序列，**块本身就是单一的信封**。信封结构（见 02）：

```
密文块：magic(8B) + version(1B) + flags(1B) + uuid(16B) + nonce(12B) + keyId(8B) + ciphertext + tag(16B)
明文块：magic(8B) + version(1B) + flags(1B) + uuid(16B) + payload + mac(32B, 仅 manifest 尾附)
```

- **magic（8B）= `"Zhao zhi"` ASCII**：固定魔数，判明这是不是本应用的数据块。
- **随机字节异或混淆（不显式存 xorByte）**：整个信封字节序列与每块随机 xorByte 逐字节异或后落盘；xorByte 不落盘，读取时从落盘首字节反推（`xorByte = bytes[0] ⊕ magic[0]`）解异或、校验 magic（见 02）。每块落盘字节随机化，外部看不到固定 magic/内容模式。
- **flags 位标记**：`0x01`=密文 / `0x02`=明文。明文块负载为明文字节（无 nonce/keyId/tag），密文块负载为加密后的密文。
- **uuid（16B）**：本数据对象自己的 UUID。**AAD = 块级时间戳（规范 ASCII 十进制字符串，即落盘前缀原文）‖ 整个信封头（magic/version/flags/uuid/nonce/keyId）**，tag 覆盖信封全部信息 + 密文 + 时间戳，防密文被搬运到别的对象、防算法版本降级、防头部字段被篡改。
- **nonce（12B，仅密文）**：96 位随机；置于 keyId **前**——解析时先读 nonce（作 keyId 派生的 seed）再读 keyId。
- **keyId（8B，仅密文）**：`dekId = SHA256(DEK)[0:8]` 为内部标识（索引键）；`keyId = 对合(repoKeyIdSeed ‖ nonce, dekId)`（镜像 Feistel 对合，可逆）。nonce 每密文随机 → 同密钥的 keyId 独立随机（**防关联**）；对合可逆 → 解密从 (nonce, keyId) 恢复 dekId 定位候选 DEK（见 02）。`repoKeyIdSeed`（32B）为**仓库级 keyId 派生种子**，存于 data 根对象 JSON，解锁时读取；每 DEK 在 `KeyIdIndex` 仅 1 条索引（以 dekId 为键）。
- **负载**：明文负载或密文。密文块的明文负载先 **deflate 压缩**再加密（降低冗余与长度暴露）。

## manifest 明文引导块

仓库必须有一条**明文**信息（KDF 参数 + salt + 算法版本 + 根对象 uuid）才能先生效 KEK 再去解锁——它不能放进密文块（解不开就死锁）。这条信息做成一个 base58 **明文块**（`flags(0x02)`），与其余对象同构、外观统一，没有独立特殊文件。

manifest 的明文 JSON 负载：

```json
{
  "version": 1,
  "type": "manifest",
  "cryptoVersion": "gcm-siv-1",
  "kdf": "argon2id",
  "salt": "<base64>",
  "params": { "m": 262144, "i": 3, "p": 4 },
  "rootObjectUuid": "<根对象 uuid>",
  "updateTimestamp": 1
}
```

- 负载统一为 JSON（含 `version`/`type`，与其余对象同构）。
- `cryptoVersion`：算法套件版本，见 02 版本化适配。
- `kdf`/`salt`/`params`：解锁前必须的 KDF 参数（派生 KEK）。
- `rootObjectUuid`：**仓库唯一根对象**（type=root）的 uuid，解锁时 O(1) 定位、KEK 试解出 root DEK 与 repoKeyIdSeed（见"仓库布局"）。
- **MAC 尾附于块末**（不在 JSON 内，与密文 tag 位置对应）：`HMAC-SHA256(macKey, 时间戳(ASCII) ‖ 完整信封头 ‖ 负载)`；`macKey = HKDF-SHA256(KEK, "sanctum-manifest-mac", 32B)`，防篡改/降级（见 02）。
- **如何识别它**：扫描全部块，找到唯一的明文块且负载 `type == "manifest"` 者即取作 manifest——**不依赖固定 UUID、不依赖文件名**。
- 明文 + MAC（同 02）：解锁后先验 MAC，篡改/降级则拒绝打开。

## 仓库布局

```
库根 (普通仓库) 或 { standalone.json, lib/, 启动脚本, 两层目录 } (独立仓库，无 data/ 层)
├── <manifest 明文块>            -- KDF 参数 + salt + 根对象 uuid（type=manifest，见上）
├── <根对象密文块>               -- 唯一根对象（type=root，持 KEK 包裹的 root DEK + repoKeyIdSeed）
└── {xx}/                        -- uuid 无连字符 hex 前 2 字符（git 风格两层目录分片）
    └── {rest}.md                -- 一文件一块（UUID 命名，内容 timestamp:base58）
```

- **单一 data 根对象**：仓库只有一个根对象（`type=root`，`RootTag.DATA`），由 manifest 的 `rootObjectUuid` 定位（O(1)）；其负载持**用 KEK 包裹的 root DEK** 与 **repoKeyIdSeed**。普通对象树内子文件夹 DEK 用**父 DEK**包裹（链式），存于各 group 的 `dek` 字段（见 05）。**没有** icon/sshKey 各自独立 root DEK——图标、SSH 密钥、远端配置的加密归属都走 data 根 DEK，仅按节点类型分树（见 05）。
- **无独立特殊文件**：manifest 是明文 base58 块，根对象与其余密文对象同构。
- 库**不强绑定 git**：普通文件夹即可用；是否 git、是否启用同步按"库形态与 Git 关系"判定。启用同步时库根即 git 仓库根。
- 仓库内**无用户内容明文对象**（当前适配器除 manifest 明文引导块外全密文）；库根文件外观一致，外部无法区分明文/密文。

## 存储引擎接口（内部，不对外暴露）

`ObjectStore` 是 core **内部**的存储引擎接口，只供进程内上层（适配器/同步）调用，**不通过网络/HTTP 暴露**：

```java
public interface ObjectStore {
    byte[] get(UUID blockUuid, Codec codec);                 // codec == null 视为裸明文读取
    void put(UUID blockUuid, byte[] data, Codec codec, String timestamp); // 覆盖对应文件；timestamp 为规范 ASCII 十进制字符串（落盘前缀原文，亦作 AAD）
    void delete(UUID blockUuid);                             // 物理删除对应文件
    List<UUID> list();
    List<Block> scan();
}
```

- 不感知上层结构；key（UUID）命名空间由适配器约定，路径由存储层按 uuid 前 2 字符分片派生。
- 本引擎**无 GC**：覆盖即替换，历史由 git（启用同步时）管理；孤立块清理由上层 `GarbageCollector` 显式提供（见"孤立块与 GC"）。
- 无 `commit`/`ChangeSet`：单块写即落盘，无提交语义；git 提交移入 app 侧 `SyncService`（见 06）。

## 读写管线

**读（get / scan）**：
- `get(uuid)`：由 uuid 派生路径 `{前2字符}/{剩余30字符}.md`，读文件、解析 `timestamp:base58`、解异或、校验 magic → 得块。未找到返回 null。
- `scan()`：`Files.walk` 遍历两层目录下所有 `.md`，逐个解析为 `Block`（文件 + 行号=1 + 时间戳 + base58 + 原始字节 + 解异或字节）。损坏/不可识别文件跳过。
- 上层拿到块后各自解析：明文 → 直接读负载；密文 → 用 (nonce, keyId) 恢复 dekId 查索引、GCM-SIV tag 试解（见 02）。

**写（put）**：编解码（若 codec 非 null）→ `{timestamp}:{base58}` 写文件（创建父目录、覆盖写）。每次写都是整文件覆盖——一文件一块，无需原位替换/重定位。

**新建**：与写相同——按新对象 UUID 派生路径创建文件。

**删除（delete）**：物理删除对应文件（一文件一块，无需软删除）。

## 孤立块与 GC

数据结构完整性由**更上层**保证（见 05）；底层不维护连通性。仓库中可能存在**无法连接到引用网络的孤立块**（条目删了但字段块还在、半写入的中间态）。上层提供显式 GC：

- **`model.impl.GarbageCollector.collect()`**：从根集合出发，沿归属边(parent)与引用边(icon/keyRef)遍历，不可达的孤立块删除并返回 uuid 列表。
- **根集合**：所有明文块（含 manifest）+ manifest 记录的 `rootObjectUuid` 根对象。
- **归属边（parent，层级，自下往上）**：group/entry/field/icon/sshKey/remote → `parent`（父对象 uuid）。
- **引用边（非归属，仅可达性）**：group/entry → `icon`；remote → `keyRef`。两者均为统一引用结构 `Ref`
  （见 05「统一引用结构 Ref」）：`node` 方案引用仓库内数据节点（id 为节点 uuid，GC 据此标记可达），
  `builtin` 方案引用应用内置资源（如内置图标，不进对象库，GC 忽略）。遍历逻辑集中在 `RefScan` 声明的
  字段表，新增引用类型只改表、不改遍历代码。
- **遍历**：队列从根出发沿归属边与引用边扩展；`孤立 = 全部块 − 可达`。

孤立块**无害**（git 历史兜底），gc 是显式、可审查的操作（`Sanctum.collectGarbage()`），不做自动清理。

## 库形态与 Git 关系

**库不强绑定 git**：库就是一个普通文件夹，管理器随时可读写。git 是可选的外层，取决于该文件夹的实际处境：

- **普通仓库**：目录本身就是数据根（两层目录 + md 块）。
- **独立仓库**：目录含 `standalone.json`（形态判定文件）+ `lib/`（全量 jar）+ 启动脚本（跨平台双头脚本，依赖本地 JRE、git 可选）。**数据块（两层目录 + md）直接建在仓库根，无 `data/` 层**。应用从独立仓库内启动时，jar 检测自身同目录/工作目录的 `standalone.json` → 孤立形态，直接解锁该仓库。
- **文件夹在 git 仓库内，且基本只有 markdown 对象**（判定为"本应用的库"）：提供同步功能——用本地 git 自动 init 若缺、commit / pull --rebase / push 与远端同步（见 06）。

**形态判定（落 jar 内，不依赖脚本传参）**：
- jar 启动时检测**当前工作目录**与 **jar 所在目录**是否存在 `standalone.json`：存在 → 独立仓库形态；否则应用形态（进入历史仓库列表页）。
- 普通仓库/独立仓库的打开判定：目录含 `standalone.json` → 独立仓库（数据根为目录本身）；目录下存在 md 块文件 → 普通仓库；否则非仓库。

**完全托管**：库根所有 markdown（含用户手动改动的）都纳入 commit/push/pull；管理器只读写自己的块，同步时把所有文件一起提交。
- 同步与否不影响**存储语义**：无论是否在 git 里，块识别、读写完全一致。
- 远端配置/密钥对象照常存为块（见 06），仅当启用同步时被读取用于本地 git。

## 明文与密文

- 当前适配器**全库密文**（除 manifest 明文引导块），读写路径统一走 CipherCodec；引擎层保留 codec==null 裸明文能力（无信封、无验证）备用。
- **加密粒度 = 对象粒度**：改一个对象只覆盖一个文件（保持"明文局部修改→密文局部修改"）。

## key 与元数据泄露

key 即文件名（随机 UUID）：零信息量（不含任何用户命名、无明文/密文前缀）；字段名、条目名等用户命名**从不进入 key**（字段对象按 UUID 引用，见 05）。

**物理边界**：对象存在性、数量、大小仍可见。对策：明文负载先 deflate 压缩再加密，降低冗余与长度暴露；结构信息（字段名/数量/归属）藏于加密的条目记录内（见 05）。

## 写路径与原子性、局部性

- 单 key：编解码（加密）→ 写文件（创建目录 + 覆盖写；文件内容仅一行 `timestamp:base58`）。
- 一次写操作 = 一个对象文件的覆盖；对象间无跨文件原子性（崩溃中间态由 git 历史兜底，见 06）。
- 单进程内 ObjectStore 串行化写入。
- 改一个块 = 只覆盖那一个文件，git 只见对应文件的一个局部 diff；不启用 git 时改动直接落盘，无 commit 概念。

## 一致性

- **底层不保证连通性**：块集合可能含孤立块，这是可接受状态。
- **完整性由上层维护**：上层以块内 UUID 构建引用图（解锁时扫描全部块、按解密负载的 type 分类、在内存构建），损坏/缺失只影响该对象，目录可随时重建（见 05）；锁定即丢弃，无持久索引。

## 限制与恢复

- **manifest 块丢失/损坏**：manifest 是明文引导块（负载 type=manifest）。若其文件被删或损坏，仓库失去 KDF 参数 + salt + 根对象 uuid，**无法解锁**。恢复路径：用 git 历史（启用同步时）还原；未启用 git 时需用户从备份恢复。不提供"从密码重建 manifest"。
- **根对象（root DEK）丢失**：仓库无法解锁（root DEK 遗失）。同理靠 git 历史/备份恢复。
- **单块大小上限**：一块 = 一个 base58 串，建议 ≤ 64 KB 原始字节（当前适配器全对象单块；大对象需扩展分块规则，暂未启用）。

## 隐私边界

- **对象块不可区分**：根对象、组、条目、字段、SSH 密钥、图标、远端配置外观统一；是否密文、所属密钥组、是根对象还是条目均不在明文可见（判定信息在块内）。
- **仍泄露的对象级信息**：仓库里存在若干长 base58 串、文件数量与大小。
- **字段名/条目名/归属关系安全**：只在解密负载内，markdown 明文不含任何用户命名。
