# 02 加密设计

## 密钥层次

```
master password
   └─ Argon2id (自研，RFC 9106；BLAKE2b 纯 Java 实现) ─> KEK (256 bit)
        └─ 直接加密 根对象（唯一 data 根对象，type=root，持 repoKeyIdSeed + rootDek 对；
           uuid 由 KEK 单向推导）
KEK 解出 rootDek（= root 组的活跃 dek2）
   └─ rootDek ──> 加密 顶层对象 / 图标 / SSH 密钥 / 远端配置（parent 指向根 uuid 的对象）
   └─ 各 group 持 dek1/dek2 双 DEK（组块由父 DEK 加密）──> 父 DEK 加密 子节点（链式，可任意深度）
KEK / 各 DEK → HKDF-SHA256 → encKey → AES-256-GCM-SIV 加密该归属下的对象
```

- KEK：由主密码经 Argon2id 派生，不落盘。
- **唯一 data 根对象**：仓库只有一个根对象（`type=root`），其 uuid 由 KEK 单向推导（`RootUuid.derive`）O(1) 定位；根对象块整体以 **KEK** 加解密，负载持 **repoKeyIdSeed** 与 **rootDek 对（dek1/dek2，明文 base64）**。顶层对象（parent 指向根 uuid 的组/条目/图标/SSH 密钥/远端）一律用 **rootDek**（root 组的活跃 dek2）加密，**没有** icon/sshKey 各自独立的 root DEK。
- **普通对象树（DEK 链）**：每个 group 持 **dek1/dek2 双 DEK**（dek1 退役中、dek2 活跃，明文 base64 存于组块、组块由父 DEK 加密），实现链式包裹（父组 DEK 加密子组块，可任意深度）。组内条目/字段用该组活跃 `dek2`（经 HKDF 派生 encKey）加密，keyId 指向所属组 DEK；顶层条目/字段与顶层子分组用 **rootDek**（root 组的活跃 dek2）。
- 各 DEK 只在解锁期间驻留内存；解锁时先以 KEK 直接解出根对象（uuid 由 KEK 推导定位）取得 repoKeyIdSeed 与 rootDek 对，顶层对象以 rootDek 解出；再沿普通对象树逐层解出各子组的 dek1/dek2。
- **根对象识别**：根对象 uuid 由 KEK 单向推导（`RootUuid.derive = HMAC-SHA256(KEK, "sanctum-root-object-uuid-v1")[0:16]`），**不记录于 manifest**，解锁 O(1) 定位，无需遍历试解；KEK 试解确证。
- **换主密码 = 重写根对象 + 顶层块**：根对象 uuid 由 KEK 单向推导、随 KEK 变化，故以新 KEK 重写根对象（新路径）；rootDek 值不变，顶层块（parent 指向旧根 uuid）改指新根 uuid 并以同一 rootDek 重写；更深层级子组 DEK 链**不动**。+ 更新 manifest 的 MAC（KEK 派生验证密钥随主密码变化）。salt 终身不变。
- 子密钥：encKey 由 HKDF-SHA256 从各 DEK 派生。

## 算法接口策略

- **标准算法走 JDK JCA 接口**（`javax.crypto`）：HMAC-SHA1/SHA256、SHA-256、AES 块引擎（`AES/ECB/NoPadding` 裸块变换）、密钥生成、SecureRandom；代码只依赖标准接口，可移植、可换 provider。
- **JDK 没有的组合算法为自研纯 Java 实现**（零第三方加密依赖）：
  - **AES-256-GCM-SIV（RFC 8452）**：集成实现 `GcmSiv`——密钥派生（counter 块取前 8 字节）、POLYVAL（GF(2^128) 小端字序，`dot(a,b)=a·b·x^-128`）、tag、CTR 单类承载；底层 AES 块引擎复用 JDK。抗 nonce 误用（RFC 8452），允许结构化/随机 nonce 两可。
  - **Argon2id（RFC 9106）**：`Blake2bDigest` + `Argon2` 纯 Java 实现（JCA 无 Argon2）。`Argon2` 同时支持 **Argon2d（type 0）** 变体，经 `Argon2Kdf.deriveRaw` 暴露，供 KDBX4 导入（KeePass 默认 Argon2d）使用，见 10。
  - **HKDF-SHA256（RFC 5869）**：自研 `HkdfSha256`（提取-扩展）。
  - **TOTP**：HMAC-SHA1 走 JDK `Mac`（RFC 2104/6238）。
- 结论：`bcprov` 依赖已彻底移除；除组合算法自研外，其余一律面向 JCA 编写。

## 熵混合（抗供应链）

所有**安全随机**（nonce、keyId、DEK、salt、UUID 生成等）不以单一 `SecureRandom` 为唯一来源，采用**混合熵**，降低对单一伪随机数生成器/其 provider 被投毒或退化的供应链风险：

- **主源**：系统 CSPRNG（`SecureRandom` / `SecureRandom.getInstanceStrong()`）。
- **叠加源**：一个独立、自维护的熵累积器（基于进程内不可控抖动，如线程调度、GC 时机、`System.nanoTime` 低位的混合）持续积累熵。
- **混合**：用 **HKDF-SHA256**（提取-扩展）合并两路熵——
  - `PRK = HKDF-Extract(salt=叠加源, IKM=主源)`：提取，把两路熵摊匀成一条均匀伪随机密钥；
  - 输出 = `HKDF-Expand(PRK, info="sanctum-entropy-mix", L)`：扩展成所需长度。
  - 任一源退化时，HMAC 单向性 + 另一源仍保证输出不可预测。
- **约束**：混合**不得降低**主 CSPRNG 的安全强度；整体仍以 CSPRNG 为骨干，叠加源仅作"不透明化"与"冗余"，不替代系统安全随机。禁止退化为纯非密码学 `Random`。
- 通过一个统一的安全随机入口提供（crypto 层内部），存储/上层不感知混合细节。与 encKey / macKey 的派生复用同一 HKDF 机制，零新增依赖。

## 版本化算法适配层（当前单版本，预留演进）

- **当前实现为单版本**：仓库只有一种信封格式，信封 `version` 字节固定为 `1`，manifest 用 `crypto` 字段记录算法套件（值 `gcm-siv-1`）。**目前不存在多版本分发 / CodecRegistry**——所有对象读写都走同一套 `CipherCodec`；信封头 `version` 字节仅作格式校验（不等于 `1` 即拒绝），不承担版本路由。
- **预留的演进形态（尚未实现）**：若将来引入新算法套件，设计上预留一个版本适配层——`manifest` 记录 `crypto` 套件标识与 KDF 参数，读路径按对象信封 `version` 字节分发到对应实现（旧仓库照常读），写路径始终用最新版本；旧对象惰性保持旧格式直到被再次写入，并可选显式迁移命令批量重写；旧实现保留供读、不删除。该 registry / 多版本分发机制**当前未落地**，本文仅描述其目标形态，避免被误读为"已存在"。
- **防降级（已实现）**：manifest 为明文，必须附带完整性校验——解锁后以 KEK 派生的验证密钥校验其 MAC（覆盖 KDF 参数等全部内容），篡改则拒绝打开；文件头 `magic` + `version` 在读取时校验，版本不符拒绝打开（见"对象信封格式"）。

## 编解码接口：Codec（内部，不对外暴露）

crypto 层提供 Codec 实现（CipherCodec），供存储引擎**每次读写注入**（见 04）；仅供进程内上层调用，不对外暴露：

```java
public final class CipherCodec implements Codec {
    CipherCodec(byte[] encKey, byte[] dek);          // 解锁流程构造；dek 用于计算 keyId
    public byte[] encode(byte[] data, long timestamp); // 加密 + magic 头 + keyId；timestamp 入 AAD
    public byte[] decode(byte[] data, long timestamp); // 嗅探 magic 判别并解密
}
```

（存储层 `Codec` 接口签名：`encode(byte[] data, String timestamp)` / `decode(byte[] data, String timestamp)`，timestamp 为块级时间戳的规范 ASCII 十进制字符串（落盘前缀原文）、作为 AAD 的一部分。）

- 密钥管理（DEK/KEK/派生/生命周期）全在 crypto 层：解锁 = 构造 CipherCodec；锁定 = 丢弃引用。
- **keyId 在 `encode()` 内部生成**：`dekId = SHA256(DEK)[0:4]`（内部标识），`keyId = 对合(repoKeyIdSeed ‖ nonce, dekId)`（见下"对象信封格式"）写入信封头——因此 CipherCodec 需持有 DEK（除 encKey 外）与仓库级 `repoKeyIdSeed` 以计算 keyId；此处的 DEK 仅供内存计算，**明文 DEK 不落盘**（落盘的是 group 对象 JSON 里的明文 base64 DEK 对，其组块由父 DEK 加密，见下）、不解出。存储引擎仍不感知密码学，不依赖 crypto（依赖反转，见 04）。

## 对象信封格式（完整性）

**验证码与内容同文件内联**：单文件原子写（temp + rename）保证内容与验证码不会撕裂；对象自包含、可自验，符合统一读写管线。分开存放无安全增益——验证码与内容同处一个存储域时，恶意储存方可一并改写；分开反而引入双文件一致性问题。

**当前仓库除 manifest 明文引导块外全密文**：所有对象（条目/组/字段/远端配置/图标）一律 SECRET，故只需一种信封；`uuid` 为对象身份，`flags` 位标记（`0x01`=密文 / `0x02`=明文，见 04）：

```
magic(6B) + version(1B) + flags(1B) + nonce(12B) + keyId(4B) + ciphertext + tag(16B)
```

- **magic（6B）= 固定魔数**（字节编码见 `BlockFormat.MAGIC`）：用于识别本应用数据块（见 04），防止把用户乱写的 base64 当数据。随 crypto 套件（manifest 的 `crypto` 字段，值 `gcm-siv-1`）演进时保持稳定。**偏移基线**：`magic` 偏移 `[0..5]`、`version` 偏移 6、`flags` 偏移 7、`nonce` 偏移 `[8..19]`、`keyId` 偏移 `[16..19]`、`ciphertext+tag` 偏移 24 起（`HEADER_LEN=24`）。明文块头不含 nonce/keyId，载荷从偏移 `PLAINTEXT_HEADER_LEN=8` 开始。
- **落盘为信封原始字节**：块序列（`magic…version…flags…nonce…keyId…ciphertext…tag`）直接落盘，无额外异或混淆。
- **uuid 不写入信封头，由块文件路径承载**：对象 uuid 即其存储路径（见 04 的 `{第1字符}/{第2字符}/{后30字符}.md` 分片布局，读取时由路径反推），块自身不自述身份。uuid 作为 AAD 的第一段参与认证（见下）——因此**块被搬到别的路径即反推出不同 uuid、AAD 不一致而解密失败**；既防搬运、防降级，又省去每块 16B 的身份字段。无文件路径的内嵌块（如分组 JSON 里的包裹 DEK、外部密钥 blob）统一以固定常量 `EMBEDDED_UUID` 进 AAD，密文变体由 12B 随机 nonce 保证。
- **nonce（12B）**：96 位随机（混合熵源，见"熵混合"）；置于 keyId **前**——解析时先读 nonce（作 keyId 派生的 seed）再读 keyId（见 04）。
- **keyId（4B）= 对合派生**（`KeyIdDeriver`）：`dekId = SHA256(DEK)[0:4]` 为内部标识（索引键，32 位）；`keyId = f(repoKeyIdSeed ‖ nonce, dekId)`，其中 `f` 为镜像 Feistel 对合（`Involution`），可逆。nonce 每密文随机 → 同密钥的 keyId 独立随机（**防关联**）；对合可逆 → 解密从 (nonce, keyId) 恢复 dekId 定位。用途与构造如下：
  - **防关联**：因 nonce 逐块随机，keyId 与 DEK 无直接可比对关系，外部无法判断哪些块共享同一 DEK（看似每块独立随机标签）。`repoKeyIdSeed`（32B）为**仓库级派生种子**，存于根对象 JSON（见"根对象与 manifest 内容"），解锁时读取；换库/换主密码场景可重新派生。
  - **可定位（索引）**：每获得一个 DEK，登记进内存哈希表 `map<4字节dekId, list<DEK>>`（`KeyIdIndex`，每 DEK 1 条条目）。dekId 仅 32 位，两个 DEK 撞同 dekId 时同桶共存，读取时以 GCM-SIV tag 试解确证区分（试解全部失败视为解密失败）；对实际规模的密钥数（几十~上百）碰撞概率可忽略。索引**随解锁动态增长**，新 DEK 一到即建条目并立即可用，不要求一次性建全。
  - **DEK 来源 = DEK 树（见 05）**：root 是隐含的"组"（键 = rootObjectUuid），持 **rootDek 对（dek1/dek2）**；每个 group 也持 **dek1/dek2 双 DEK**（组块由父 DEK 加密，链式）。新/改子节点一律用所在组的**活跃 dek2**，故任意密文块的 keyId 指向其归属组（含 root）的某把 DEK——同组条目共享其 DEK（一对多），不同组各自独立；当某组不再有子节点引用退役中的 dek1 时触发惰性轮换（dek2 提升为 dek1、新建 dek2），见 05。普通块负载**不新增 keyRef**，与哪把 DEK 配对完全由头部 keyId 决定。
  - **根对象用 KEK 加密（区别于普通块）**：根对象（type=root）整块以 **KEK** 加解密，负载持 repoKeyIdSeed 与 rootDek 对（明文 base64，无内层包裹）。根对象的 uuid 由 KEK 单向推导（`RootUuid.derive = HMAC-SHA256(KEK, "sanctum-root-object-uuid-v1")[0:16]`）：不落盘、不记入 manifest，创建与解锁两侧以同一 KEK 重算即得，O(1) 定位后 KEK 试解，得 rootDek；顶层块（rootDek 加密）随之解出，再沿组链逐层解出各子组 DEK，避免"要解 DEK 却需先有 DEK"的鸡生蛋。

- **nonce = 96 位（12B）随机**（混合熵源，见"熵混合"）：BC 的 AES-GCM-SIV 要求 12 字节 nonce（RFC 8452 推荐）；GCM-SIV 抗误用，碰撞只泄露"同明文同密文"的相等性；96 位随机碰撞概率可忽略。
- 结构化备选（不推荐，除非需要确定性 nonce）：`机器ID(32) ‖ 计数(64) ‖ 随机(32)`；**禁止时间戳入 nonce**——nonce 公开存于文件头，时间戳会泄露对象写入时间。
- **AES-256-GCM-SIV tag = 全量认证**：覆盖 ciphertext 与 **AAD**。**AAD = uuid(16B) ‖ 块级时间戳（规范 ASCII 十进制字符串，即落盘前缀原文）‖ 整个信封头（`magic ‖ version ‖ flags ‖ nonce ‖ keyId`）**——tag 覆盖 uuid + 信封全部信息 + 密文 + 时间戳。任何头部字段（keyId/nonce/flags/version/magic）、时间戳，或块所在路径（它决定 uuid）被篡改都会破坏 tag → 拒绝读取；防搬运到别的对象/别的路径、防算法版本降级、防 keyId/nonce 被改。
- **明文块（manifest）全量认证**：明文块无 AEAD tag，靠**尾附于块末的 MAC**（HMAC-SHA256，见"根对象与 manifest 内容"），**MAC 覆盖 uuid(16B) ‖ 块级时间戳（规范 ASCII 十进制字符串，即落盘前缀原文）‖ 完整信封头（`magic‖version‖flags`）‖ JSON 负载**——与密文同一顺序约定（uuid 打头），篡改任何一部分即失效。
- **为何 16B**：128 位认证强度与系统整体安全等级（256 位密钥）一致；对伪造攻击单次尝试成功率 2⁻¹²⁸，继续加长无实际增益。
- 统一读写管线：读 → 校验 magic/version → AEAD 解密验证 → 返回负载。
- 引擎层仍支持 codec==null 裸明文写（无信封、无验证），适配器当前不使用（见 04/05）。

## 完整性设计（威胁模型：防混入/篡改）

威胁模型限定为"仓库中不允许出现伪造或被篡改的对象文件"（**不防整体回滚/重放**——那是 git 历史与远端背书范畴，超出本设计）：

1. **对象级验证（内联）**：任何非本应用生成、或内容被改动的文件，tag 验证失败即拒绝读取；AAD 绑定 key 路径，把文件挪到别的 key 下同样失败。
2. **manifest 验证**：解锁后以 KEK 派生密钥校验 manifest 的 MAC，防止伪造/篡改的 manifest（含降级，见"版本化算法适配层"）。

## KDF 参数

- **Argon2id 参数可配置**：创建/换主密码时可选档位，权衡速度与安全；参数存于 manifest，打开时以 manifest 为准（各仓库可不同，向后兼容）。
  - **默认高安全档**：memory ≥ 256 MiB、iterations ≥ 3、parallelism 4。这是密码管理器（高价值、可离线暴力）的推荐起点。
  - 允许降档（如资源受限设备）但默认不降、降档需显式选择并提示风险。
- 参数随 manifest 块保存，便于将来升级迁移；打开时以 manifest 为准。

## 根对象与 manifest 内容

**根对象与 DEK 树**（根对象 `type=root`，其 uuid 由 KEK 单向推导定位）：

- **唯一根对象**：仓库只有一个 data 根对象，根对象块整体以 **KEK** 直接加解密，负载持 **repoKeyIdSeed** 与 **rootDek 对（dek1/dek2，明文 base64）**。顶层对象（parent 指向根 uuid）用 rootDek 加密；每个 group 的 **dek1/dek2 双 DEK**（明文 base64）存于组块，组块由父 DEK 加密（链式）。没有 icon/sshKey 各自独立的 root DEK——各类型节点共用同一棵 DEK 树，仅按节点类型分树（见 05）。
- **换主密码 = 重写根对象 + 顶层块**：根对象 uuid 随 KEK 变化，故以新 KEK 重写根对象；rootDek 值不变，顶层块（parent 指向旧根 uuid）改指新根 uuid 并以同一 rootDek 重写；更深层级以组 DEK 加解密、parent 指向组 uuid，**不受密码轮换影响**。manifest MAC 随验证密钥（KEK 派生）变化而重算。
- 主密码正确性校验隐含在解密成败：根对象块的 GCM-SIV tag 验证通过 = KEK 正确。
- **不含** salt 与 KDF 参数（它们在 manifest；KDF 必须先于解锁执行）。

**manifest**（明文 + MAC，MAC 由解锁后 KEK 派生的验证密钥计算；按 04 作为**明文 base64 块**存放，用负载 `type == "manifest"` 识别，负载为 JSON，无独立特殊文件）：

```json
{
  "version": 1,
  "type": "manifest",
  "crypto": "gcm-siv-1",
  "kdf": "argon2id",
  "salt": "<base64>",
  "params": { "memoryKiB": 262144, "iterations": 3, "parallelism": 4 }
}
```

> manifest **不记录根对象 uuid**：根对象 uuid 由 KEK 单向推导（`RootUuid.derive`），解锁时重算即可定位，无需落盘字段。

- `version`：JSON 结构版本；`type`：固定 `manifest`。
- `crypto`：算法套件版本（值 `gcm-siv-1`），见"版本化算法适配层"。
- `kdf`/`salt`/`params`：KDF 参数（salt 创建时随机生成、终身不变），必须先于解锁生效。
- **MAC 尾附于块末**（不在 JSON 内，与密文 tag 位置对应）：`HMAC-SHA256(macKey, uuid(16B，即固定 MANIFEST_UUID) ‖ 时间戳(ASCII) ‖ 完整信封头 ‖ JSON 负载)`——全量认证，防篡改/降级。**MAC 密钥派生**：`macKey = HKDF-SHA256(KEK, info="sanctum-manifest-mac", 32B)`。随主密码变化（KEK 变则 macKey 变），故换主密码须重算（见"换主密码"）。

## 仓库时间戳（全局写入锚点）

- **会话锚点**：解锁时扫描全库所有块，取**最大时间戳**作为会话基座 `baseTimestamp`（`WarehouseClock` 计算），**不持久化到 manifest**（manifest 不再含 `warehouseTime` 字段）。
- **每块写入时**，其时间戳（毫秒）= `max(两值)`：
  1. `(nanoTimeNow − 启动nanoTime) 毫秒 + baseTimestamp`——相对锚点：会话内单调时钟时长 + 仓库锚点；
  2. `仓库中所有块的最大时间戳`——保证不倒退。
- `nanoTime` 用单调时钟（`System.nanoTime`），不受系统改时间影响；存储单位毫秒。
- **用途**：同步冲突仲裁（时间戳大者 wins，见 06）。跨设备基于同一锚点，写入时间戳全局可比、单调。
- manifest 块的时间戳同样按此规则写入（落盘前缀，不占负载 JSON 字段）。

**解锁流程（惰性增量）**：
1. 扫描全部块，读出所有明文块（`flags(0x02)`）负载 JSON，按 `type == "manifest"` 找到 manifest（不依赖固定 UUID/文件名）。
2. 按 manifest 的 KDF 参数 + salt 派生 KEK，验 manifest MAC（防篡改/降级）。
3. 以已知密钥（初为 KEK）为**工作队列**，反复尝试解开队列能解开的块——先按 KEK 推导出的根对象 uuid（`RootUuid.derive`）O(1) 定位根对象（type=root），KEK 试解得 repoKeyIdSeed 与 rootDek 对；再沿普通对象树递归解出各子组的 dek1/dek2（父组 DEK 加密子组块）。密钥依赖可任意链式/嵌套，无需预定顺序。
4. 每得一个 DEK 即时为其建立 keyId 索引条目（`map<dekId, DEK>`，1 条/DEK）并立即用于后续查找——**索引的建立与使用交织进行，无"先全部建完再用完"的干净分界**。
5. 派生 encKey、构建内存目录（见 05）；普通块用其 (nonce, keyId) 恢复 dekId 查当前索引试解。

## 外部密钥加解密服务（外部密钥 = 字段 kind）

为外部软件提供"用库里密钥加解密数据"的能力。**不再有独立 extKey 类型**——外部密钥就是某个数据条目下的**自定义字段**，`kind = "externalKey"`，字段值即密钥材料（见 05）：

- **外部密钥**：某条目的自定义字段，`kind:"externalKey"`，值 = 密钥材料。它随条目加密存储、被条目引用即天然激活（GC 可达），无需特殊激活约束。
- **标识**：外部用该字段对象的 UUID 指定密钥（`list()` 返回激活的 externalKey 字段的 uuid + description）。
- **每个 externalKey 带描述**：字段的 `description`（或字段名）说明用途。

**接口**：
- `byte[] encrypt(byte[] data, UUID fieldUuid)` → 密文
  - 指定 externalKey 字段（UUID），取其密钥材料加密，返回密文。
- `byte[] decrypt(byte[] cipher)` → 明文
  - **外部不传 UUID**，靠密文块头自带的 `keyId` 定位解密密钥，经 **GCM-SIV tag 试解密**确证。
- `List<KeyInfo> list()` → 当前**可用**（`kind == "externalKey"` 且被引用激活）字段的 `uuid` + `描述`。

**隔离与防泄漏（关键）**：
- **解密候选域 = 仅 `kind == "externalKey"` 的字段密钥**。系统密钥（KEK / rootDek / 各组 DEK 对）的 keyId **不在**外部解密的候选里，外部即使传入"恰等于某系统 DEK keyId"的密文头，候选集中无系统 DEK → 试解失败 → 拒绝。**不会路由到系统密钥**。
- **加密指定 UUID 时**，只接受 `kind == "externalKey"` 的字段；指向系统对象/普通字段 → 拒绝。
- 外部密钥与系统密钥（rootDek / 组 DEK）语义隔离：外部密钥只服务外部数据，系统 DEK 只加密库内对象。

### HTTP 传输（本地，JSON）

向外部程序通过**本地 HTTP + JSON** 暴露**外部密钥加解密服务**（仅此能力；不暴露任何编辑/读写仓库数据的接口）：

- **监听**：仅绑定 `127.0.0.1`（localhost），可用 JDK `com.sun.net.httpserver.HttpServer` 实现，零额外依赖。
- **范围**：仅 `/keys/list`、`/crypt/encrypt`、`/crypt/decrypt` 三个端点（外部密钥加解密）；**不提供** put/get/delete/编辑/仓库管理。
- **生命周期**：HTTP 服务**跟随应用启动**（始终监听端口）；**锁定时不提供服务**——接口保留、调用即返回错误（`locked`），不泄露任何密钥能力。
- **鉴权**：不鉴权；安全依赖"仅绑定 localhost + 本机信任模型"（见 03）。解不出/拒绝时统一返回失败，不区分"是否系统密钥"。
- **数据格式**：明文与密文统一用 base64（与内部一致）；JSON 传参。

**端点**：

`POST /keys/list`
- 请求：`{}`
- 响应：`{ "ok": true, "keys": [{ "uuid", "name", "description" }] }`（激活 externalKey 字段列表）

`POST /crypt/encrypt`
- 请求：`{ "uuid": "<fieldUuid>", "plaintextB64": "<base64 明文>" }`
- 响应：`{ "ok": true, "ciphertextB64": "<base64 密文>" }`

`POST /crypt/decrypt`
- 请求：`{ "ciphertextB64": "<base64 密文>" }`
- 响应：`{ "ok": true, "plaintextB64": "<base64 明文>" }`

**错误响应**（统一）：
```json
{ "ok": false, "error": "<code>", "message": "<说明>" }
```
- 错误码：`locked`（锁定）/ `unknown_key` / `inactive_key` / `wrong_type` / `decrypt_failed` / `bad_request`。
- 锁定期间所有端点一律返回 `locked`。

## 防降级与完整性

- 文件头 magic + version，读取时校验，版本不符拒绝打开，防降级攻击。
- `manifest` 块（负载 `type == "manifest"`）记录格式版本、KDF 参数与 crypto（算法套件，值 `gcm-siv-1`），打开仓库时先校验；manifest 的完整性由解锁后 KEK 派生密钥的 MAC 保证（见"版本化算法适配层"）。

## TOTP

- TOTP 种子作为普通字段加密存储（见 05 密码库适配器）。
- 生成验证码用 JDK `Mac HmacSHA1`（RFC 6238），无需服务端。
